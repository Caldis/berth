# 工程摩擦记录

> task: GH-135 索引引擎进度可视化 (E3 重建确认对话框)

## 发生阶段
4.0-verify (真机 CDP 截图验收, 暴露 3.0-implement 的测试盲区)

## 现象
重建确认对话框的"取消"按钮在真机渲染为 raw i18n key `common.cancel` (en/zh 均缺该键)。
全套单测 (含 settings-page.test) 全绿却没发现 —— 原因: 既有测试从不点开重建对话框,
对话框内容是 trigger 点击后才挂载的分支, 未被任何用例渲染过, `t('common.cancel')` 的
缺键泄漏因此逃逸。是 CDP 截图 (而非单测) 才看见 raw key。

## 工程师介入动作
1. 补 `common.cancel` (en: Cancel / zh: 取消)。
2. settings-page.test 增用例: 点 "Rebuild index" → 断言对话框标题 + 译文按钮
   ("Cancel"/"Clear and rebuild") + `queryByText('common.cancel')` 不存在 → 确认派发 rebuild。

## 应沉淀的上下文或规则
- **trigger 后才挂载的交互 UI (Modal/Popover/Drawer/二级对话框) 必须有"点开它"的测试**:
  只渲染父组件不点开, 子分支里的 `t()` 缺键、控件错配、派发缺失全部逃逸单测。
- **raw-key 泄漏单测可低成本兜底**: 凡新增 `t('x.y')`, 在对应"点开"用例里加一条
  `expect(screen.queryByText('x.y')).not.toBeInTheDocument()` (用点号原样字符串), 比逐键核对 i18n 文件更省。
- 单测用真实 i18n 实例时, 缺键会原样回显 key —— 这既是泄漏来源, 也是上面断言能生效的前提。
- CDP 截图是 t()/视觉层的最终兜底 (与 [[runtime-behavior-needs-real-run]] 同源): 静态绿证明不了
  "用户实际看到的字符串正确"。新增任何带可见文案的 trigger UI, 验收必须真机截图过一眼。

## 建议的流程改进
(由 harness-5.1-friction 消费)
- 3.0-implement 检查项: 新增 Modal/Popover/二级对话框时, 同 PR 必须有点开它的测试 + raw-key not-present 断言。
- 4.0-verify UI 检查项: 凡新增可见文案的 trigger UI, CDP 截图覆盖"点开态", 不只截父页面。
