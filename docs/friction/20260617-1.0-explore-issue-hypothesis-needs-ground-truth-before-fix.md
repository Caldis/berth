# 工程摩擦记录

> task_id: GH-137 · issue: docs/issues/2026-06-16-BUG-windows-incremental-watch-full-rescan.md

## 发生阶段
1.0-explore (定向), 4.0-verify (CI ground truth 确认)。

## 现象
来源 issue 把缺陷定性为 "windows 产品 bug": deriveAssetsForPath 在 windows 对 skill 返回 null (matchCapabilityGlob/inferScope 路径归一), 并建议改 `packages/berth-scan-engine/derive-asset.ts`。若照此 explore→design→implement, 会改错地方 (动产品路径归一), 既修不好又引入风险。issue 自己标了 "根因候选, 待 windows 实机定位", 但 candidate 写得很具体, 极易被当成结论直接进实现。

## 工程师介入动作 (Agent 自主, 经验证)
- 不照搬 issue 假设, 先取 ground truth:
  1. 本地 windows 实机 build + 连跑该 e2e 4 次 → **全绿, 不复现**。
  2. chokidar 真实路径探针 (临时脚本, 系统 temp, 用后删) → chokidar 4 发反斜杠路径, `matchCapabilityGlob` 对 codex `.agents/skills` 规则 dirOk+nameOk 均 true → derive 不返回 null。
  3. 现有单测 `tests/unit/derive-asset.test.ts:120` (codex `.agents/skills` skill) windows CI 绿 → 再证 derive 在 win 正常。
  4. 拉失败 CI job 日志看**实际断言值**: `before.id="initial"` vs `afterId="snapshot-..."`。
- 由此证伪 issue 的两个产品根因候选, 定位真因: **e2e 时序缺陷** —— GH-135 渐进 partial 让 seed 在首扫 commit 前 (id 仍 'initial') 即可见, 慢 runner 上 poll 抢在 commit 前捕获 before.id='initial', 随后 commit 铸新 id。修复是纯测试 (等 `snapshot.id !== 'initial'` 再捕获基线), 零产品代码。windows CI 转绿确认。

## 应沉淀的上下文或规则
1. **docs/issues 的根因/解法是待验证假设, 不是 ground truth。** explore 定方向前, 对 "X 平台产品 bug" 这类判断必须先实机复现 / 拉 CI 实际断言值 / 写最小探针证伪或证实, 再决定改产品代码还是测试。issue 写得越具体越要警惕被当结论。与 GH-117 同构 (e2e 时序/隔离被误报为 macOS 平台 bug)。
2. **平台特异 e2e 红, 本地同平台不复现时, 优先怀疑时序而非平台逻辑。** 第一步拉失败 job 的实际 Expected/Received, 值的形态 (如 `"initial"`) 往往直接点出机制。
3. **渐进 partial 流式扫描下, e2e 把 `snapshot.id` 当稳定基线前必须先等首扫 commit (`id !== 'initial'`)。** commit 前 partial 已让资产可见但 id 仍 'initial'; 慢 runner 上提前捕获基线 = 把"首扫 commit"误判成"增量破坏了 id"。产品不变量 (applyFileChange 保持 id) 由平台无关单测覆盖即可, 不必靠 e2e 兜时序。
4. 探针/实验脚本写系统 temp、用后即删, 不入仓库 (invariant 21)。

## 建议的流程改进
(由 harness-5.1-friction 消费) 在 1.0-explore playbook 增一条: 当 source 是 docs/issues 且其中含具体"根因候选/平台 bug"判断时, explore 第一步是取 ground truth (实机复现 / CI 实际断言值 / 最小探针) 证伪或证实该判断, 再定改动面; 不得直接把 issue 候选当结论进 design。
