# 工程摩擦记录

## 发生阶段

GH-107 file-viewer drawer 贴顶。过度防御在 2.0-design 引入, 4.0-verify 用户验收暴露。

## 现象

Explore 英文检索到 Electron `hiddenInset` 顶部区 `-webkit-app-region: no-drag` 的边缘 case bug (maximize/restore 后按钮失效, electron #17425/#41695/#39885), 据此在 design 把方案从"简单整屏贴顶 (B)"升级为带防御的 C1: 加 macOS `titlebar-drag` spacer 把 header 按钮压到顶部 40px 系统区之下, 并保留 backdrop `top-10` 不盖左上红绿灯条。CDP 实测坐标 + 全套测试全绿, Agent 自认 verify 通过。

用户验收第一时间指出两个视觉问题: "遮罩层没有到顶" (backdrop top-10 留的 40px 亮带) 和 "右上角按钮偏下" (spacer 把按钮压下 40px)。两者都是 C1 防御的直接副作用。用户要的是简洁的整屏贴顶 (方案 B), 不在意那些边缘 case 防御。

## 工程师介入动作

- 退回 implement 改回方案 B: backdrop `fixed inset-0` 全屏遮罩到顶; 移除 spacer 让 header/按钮贴顶; drawer 保持 `top-0 h-full`; header `titlebar-no-drag` 保 close 可点。
- close 因此回到 macOS 顶部系统区, 其可点性 (用户两次强调的历史红线) 改由真实实测 / 用户在自己 dev 窗口确认把关。

## 应沉淀的上下文或规则

- **边缘 case 的理论风险 (尤其低频窗口状态如 maximize/restore) 不能凌驾于用户明确的视觉/交互预期。** 查外部 SDK 的坑 (不变量 9) 是对的, 但"查到坑"不等于"必须加结构去抵消它"。当防御有可见视觉代价 (多出空白条 / 遮罩不到顶 / 按钮偏移) 时, 等于用确定的体验损失去赌一个低频 bug, 多半不划算。
- **正确做法**: 先用最简、最贴合用户预期的方案落地; 把边缘风险作为"已知限制"写进 `docs/issues/`, 或在验收时一句话告知用户由其定夺, 而不是 Agent 自作主张加防御元素。布局 taste 决策 (贴顶、遮罩范围、按钮位置) 以用户实际要的样子为准。
- **主观视觉验收必须尽早把"长什么样"交给用户判断**, 不能因为"CDP 坐标对 + 测试全绿"就自认视觉通过 — 坐标和测试只证明实现符合 Agent 自己定的方案, 证明不了那个方案是用户要的。涉及主观视觉的改动, 截图给用户看 / 让用户在自己 dev 窗口看, 应早于宣布 verify 通过。

## 建议的流程改进

(由 harness-5.1-friction 消费)

- 2.0-design: 当基于外部 SDK 边缘 case 要新增带可见视觉代价的防御结构 (额外元素 / 偏移 / 平台分支) 时, 列为"待用户确认"的设计选项, 不默认采纳; 或先落无防御的简洁版, 把边缘风险写进 issues。
- 4.0-verify: 主观视觉改动 (布局/间距/贴顶/遮罩) 的验收, 优先产出给用户看的截图并显式请用户确认"是不是你要的样子", 再跑机械门禁; 不把"测试绿 + 坐标对"当作视觉验收通过。
