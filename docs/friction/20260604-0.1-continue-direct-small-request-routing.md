# 明确小需求不应二次确认 harness 豁免

> 命名: docs/friction/{YYYYMMDD}-{action-id}-{summary}.md
> action-id: 0.0-new|0.1-continue|1.0-explore|2.0-design|3.0-implement|3.1-polish|4.0-verify|5.0-archive|5.1-friction|5.2-issues
> 可在正文交叉引用 task_id / issue, 不拆子目录。优化后移入 _archive/。

## 发生阶段

非 harness 的小改动继续处理路径。

## 现象

用户在 Hooks connector 调整过程中给出了明确目的、范围和具体参数, 例如:

- "竖线计算小调整, 向左偏移 1px"
- "throttle 改 300 ms"
- "500 太长了, 改 100"

这类请求已经足够明确, 影响范围也局限在现有组件和对应测试。Agent 仍按既有 "小改动豁免前必须征得用户确认" 规则倾向先解释流程, 会增加一次无意义等待。

## 工程师介入动作

确认问题有效: 本类请求不是新 feature / bug 任务, 不需要新建 `docs/works/` 任务态; 但仍需要窄路径实现、目标测试和必要 typecheck。

已将规则改成两级:

1. 用户已经明确给出目的、范围或具体参数, 且改动满足小改动条件时, Agent 直接声明按小改动处理并执行, 不再二次询问是否跳过 harness。
2. 用户只给出模糊目标, 需要 Agent 自行判断是否小改动时, 仍先声明豁免依据并等待确认。

## 应沉淀的上下文或规则

小改动直接处理的前提:

- 用户已明确授权直接处理, 或请求本身已经包含明确目的、范围、具体参数 / 文件 / UI 部位。
- 影响面局限在单一文件或少量紧密相关文件。
- 不涉及主进程/IPC/数据契约、外部产品行为、跨模块根因分析、新功能设计或人工意图澄清。
- 可用目标测试、目标 lint/typecheck 或明确的局部验证说明完成验收。

如果实施中发现影响面超出上述边界, Agent 必须停下, 说明原因, 并切回 harness 或请求用户确认。

## 建议的流程改进

(由 harness-5.1-friction 消费)

- 在 `AGENTS.md` 和 `.agents/workflow/_shared.md` 中区分 "用户显式明确的小需求" 与 "Agent 自行判断的小改动豁免"。
- 前者直接执行, 后者才需要先问。
- 直接执行仍必须保留窄路径暂存、目标验证和提交前 staged 核对。
