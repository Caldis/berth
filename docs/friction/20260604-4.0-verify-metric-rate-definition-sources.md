# 速率类指标实现前必须先确认统计口径

## 发生阶段

GH-95 会话详情页 token 速率修复, verify 阶段用户追问并纠正: 不能凭经验设定 token 速率计算规则, 需要先确认是否有权威来源、参考文档或开源实现。

## 现象

实现先用 `usageDuration >= 60` 作为保守阈值避免短窗口外推, 但设计产物没有先引用官方文档或成熟开源项目来定义 `tok/min` 的统计口径。这样虽然能压住离谱数值, 仍可能把一个经验性防护误写成准确指标。

后续把指标改名为 token 消耗速率并展示公式后, 真实 Codex 会话仍出现 `884515.8 tok/min` 这类数值。公式透明只能解释数字来源, 不能让语义不可靠的指标变得适合默认展示。

## 工程师介入动作

补查 Claude Code monitoring 文档与开源实现:

- Claude Code 官方文档提供 token usage、active time、request `duration_ms` 等遥测字段, 但没有定义 session detail 的 `tok/min` 展示口径。
- `ccusage` 的 burn rate 用 block 内首尾 entry 时间跨度计算 `tokens/minute`, 并对无时间跨度返回 unavailable。
- `Claude-Code-Usage-Monitor` 的 burn rate 对 active block 且持续至少 1 分钟时才计算 tokens/minute。
- `vscode-claude-status` 使用最近 30 分钟窗口估算成本消耗速率, 而不是会话级 `tok/min`。

## 应沉淀的上下文或规则

速率、趋势、预测类指标在实现前必须先写清:

- 分子: 使用总 token、增量 token、非缓存 token 还是成本。
- 分母: 使用 API request duration、usage event span、active block span 还是 rolling window。
- 窗口: 最短可计算时长、最少样本数、滚动窗口长度。
- 语义: 这是模型吞吐率、会话消耗速率, 还是限额消耗速度。

如果官方没有公开定义, 只能标注为本地估算或参考开源实现的经验规则; 不应在 UI 上显示成权威速度指标。

如果真实样本已经证明该指标会稳定产生误导性大数, 不应继续追加阈值、cap、窗口切分等补丁。默认策略应改为 placeholder, hover 解释为什么暂不计算。

## 建议的流程改进

Explore / Design 遇到 `rate`, `velocity`, `burn rate`, `projection`, `usage per minute/hour` 等指标时, 在方案前增加一个 "metric definition" 小节, 先列来源与不可证明点。没有来源、样本不足, 或实测值会误导用户时, 默认显示 placeholder, 不做外推计算。公式透明是必要条件, 不是充分条件。
