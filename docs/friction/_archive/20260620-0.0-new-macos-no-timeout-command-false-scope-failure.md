## 发生阶段
0.0-new — 建 work 前验证 gh project scope 可用性时。

## 现象
用 `timeout 30 gh project list --owner Caldis` 探测 gh project scope, bash 报 `command not found: timeout`, 命令整体非 0 退出, 被误判为 "project scope MISSING", 差点据 0.0-new 的"缺 scope 则 STOP"规则中断建 work。实际 `gh auth status` 明示 token 含 `project` scope, 去掉 `timeout` 重跑 `gh project list` 正常返回 (berth = PVT_kwHOADXbEs4BZHvQ)。

## 根因
macOS 默认无 GNU coreutils 的 `timeout` 命令 (Linux/CI 有, 本机 darwin 无)。`timeout ... <cmd>` 在 macOS bash 直接 `command not found`, 与 `<cmd>` 本身成败无关 — wrapper 不存在伪装成被测目标失败。

## 应沉淀的规则
- **macOS bash 不要用 `timeout` / `gtimeout` 包裹命令** (除非已确认 `brew install coreutils`)。需要超时控制时改用命令自带超时参数、`perl -e 'alarm N; exec @ARGV' <cmd>`、或后台 + sleep + kill。
- **能力/scope 探测失败先排除"探测器本身不存在或不可用", 再判定被测目标失败**。尤其 gh scope / 权限 / 二进制存在性探测报失败时, 先看是不是 wrapper (timeout / 特定 flag) 的问题, 不据假阴性触发 STOP / blocked 分支。
- 上次会话已跑通的能力 (harness-projects ensure / gh project) 这次探测报失败, 优先怀疑探测方式而非真失效。
