# 提取型对账断言在集合意外为空时空洞通过 (⊆/forEach 形断言无非空钉)

- action: 3.0-implement
- 日期: 2026-07-04
- 任务: GH-154 (T4 typed sendToWindow 迁移)

## 现象

把 `webContents.send` 迁移为 `sendToWindow` 后, `ipc-contract.test.ts` 的 eventsSent 提取 regex 未同步更新, 提取集合变成**空集** — 但测试仍然全绿: "实发 ⊆ 订阅" 断言写成 `for (const sent of eventsSent) expect(...)`, 空集合零次迭代零次断言, 空洞通过。恰逢同步该 regex 的 `node -e` 字符串 replace 因转义差异**静默 no-op** (无匹配也不报错, 还打印了成功 log), 两层静默叠加 — 对账网在无人察觉下失效了一个提交周期 (靠提交后复核 staged 集合发现该文件根本没进 diff 才暴露)。

## 根因

1. ⊆/forEach 形断言天然对空集合免疫 — 提取源漂移 (regex 不再匹配任何调用点) 表现为"检查消失"而不是"检查失败"。
2. `node -e "s.replace(...)"` 类脚本编辑无匹配时静默成功; 打印的 "updated" log 是脚本自己说的, 不是事实。

## 处理

- `ipc-contract.test.ts` 实发集合断言前加 `expect(eventsSent.length).toBeGreaterThan(0)` — regex 再漂移即红。
- regex 改用 Edit 工具补正 (精确 old_string 匹配, 不命中即报错)。

## 教训

- **凡"从源码提取集合再对账"的测试, 每个提取集合都要钉非空下界** (或钉已知精确值); ⊆ 断言必须搭配基数断言, 否则提取面漂移 = 静默放弃检查。
- 脚本化文本编辑 (node -e / sed) 的"成功输出"不可信, 必须以事实核验收尾: `git diff --stat` 看文件真的变了, 或 grep 新模式非零。Edit 工具的 "old_string 不匹配即报错" 特性在这类小编辑上优于脚本。
