# 工程摩擦记录

## 发生阶段
3.0-implement (GH-116 T3, engine 指纹缓存测试)

## 现象
为 AssetFileCache 指纹缓存写"同内容长度+还原 mtime → 命中缓存"的测试时, 用 `const stat = fs.statSync(f); fs.writeFileSync(...); fs.utimesSync(f, stat.atime, stat.mtime)` 还原 mtime, 期望指纹不变命中缓存 — 实际 MISS (缓存未命中, 重新解析)。两个测试文件 (session-replay-engine / session-detail) 同时踩中。

## 工程师介入动作
无 (Agent 自查): `statSync().mtimeMs` 在 Windows 上带**亚毫秒小数** (如 1718071234567.123), 而 `utimesSync` 接受 Date, 只有**毫秒精度** — 还原后 mtimeMs 小数部分丢失, `sameFingerprint` 的 `mtimeMs` 全等比较失败。

## 应沉淀的上下文或规则
- 测试要构造"指纹相同"场景时, **不能事后还原 statSync 捞到的 mtime**; 必须在首次 parse 前就用 `fs.utimesSync(f, fixed, fixed)` 把 mtime **钉到整毫秒的固定 Date**, 后续重写文件后再钉同一个 fixed Date。
- 仓库先例: `tests/unit/codex-session-parser.test.ts` 的缓存测试即用固定 Date 模式 (它靠 size 变化触发失效, 没踩到还原路径)。
- 适用面: 所有依赖 `path+size+mtimeMs` 指纹的缓存测试 (AssetFileCache 全部消费方)。

## 建议的流程改进
(由 harness-5.1-friction 消费) 可在 `.agents/workflow/3.0-implement.md` 的实现期跨切面约束中追加一条: "指纹缓存 (mtimeMs) 类测试构造同指纹场景时, 先钉整毫秒固定 mtime 再 parse; 禁止 statSync 捞 mtime 事后还原 (utimesSync 只有 ms 精度, Windows mtimeMs 带亚毫秒)"。
