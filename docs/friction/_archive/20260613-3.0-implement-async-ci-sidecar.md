# 工程摩擦记录

## 发生阶段

3.0-implement, GH-125 顶部标题栏与搜索输入框统一任务。

## 现象

完成一个已验证小步并 push 后, Agent 把 GitHub Actions 当成同步闸门, 多次执行 `pnpm harness:ci:wait --sha ...` 并等待数分钟。CI 很重要, 但单次 run 很重; 在实现阶段每个小步都同步等待, 会让主开发循环被远端队列和跨平台 job 阻塞。

## 工程师介入动作

用户指出: CI 应作为异步行为执行, 不应阻塞开发任务。Agent 应通过子代理检查 CI 状态; 如果 CI 失败且失败原因会严重影响主循环当前任务, 才优先修复。否则 CI 问题可以延后到最终收口时一起处理。

## 应沉淀的上下文或规则

- 小步提交和及时 push 仍然保留; 本地目标测试、typecheck、harness check 仍是当前小步的主要门禁。
- 实现阶段 push 后, 主 Agent 不同步等待 GitHub Actions 完成; 应启动旁路子代理或等价异步检查记录 CI 状态。
- 子代理只做远端状态检查和失败归因, 不改代码, 不阻塞主实现。
- 若子代理确认 CI 失败来自当前会话提交, 且失败会直接破坏当前任务的主线行为或后续实现基础, 主 Agent 应暂停新功能推进并先修复。
- 若 CI 仍在运行, 或失败与当前任务无关、可在 verify 统一修复, 主 Agent 继续当前实现, 在 verify/archive 前统一消费 CI 结果。

## 建议的流程改进

修改 workflow 共享契约: 把 implement 阶段 push 后的 `harness:ci:wait` 从同步必等改为异步旁路检查; 只在 verify/archive/完成声明前要求消费远端 CI 成功结果。工具索引中标明 `harness:ci:wait` 是远端收口/旁路检查工具, 不是每次小步 push 后阻塞主循环的工具。
