# 工程摩擦记录

> 命名: docs/friction/{YYYYMMDD}-{action-id}-{summary}.md (action-id: 0.0-new|0.1-continue|1.0-explore|2.0-design|3.0-implement|3.1-polish|4.0-verify|5.0-archive|5.1-friction|5.2-issues)
> 可在正文交叉引用 task_id / issue, 不拆子目录。优化后移入 _archive/。

## 发生阶段
archive (任务收尾归档时), 但根因贯穿整轮的 git/shell 操作纪律。

## 现象
两个反复出现、用户两次问"怎么一直报错"的过程失误:

1. **`git add -A <dir>` 在共享工作树吞掉他人 untracked 旁支**。归档 memory 任务时执行
   `git add -A docs/works/`, 误把另一并行 session 的 untracked 任务目录
   `2026-05-30-status-line-capability-compatibility/` (5 个文件) 一并暂存并提交进我的 archive
   commit。靠 `git reset --soft HEAD~1` + `git restore --staged <他人目录>` 才救回, 他人文件内容零丢失。

2. **批量并行命令 + 失败命令 + Windows 不存在的 `/tmp` → 满屏假错误**。把 ~10 个命令放进单个
   并行 batch, 其中一个用了 `/tmp/xxx` (Windows 上解析为不存在的 `D:\tmp\` → ENOENT); harness
   对并行 batch 的规则是"任一调用失败则整批 Cancelled", 于是 1 个真错被放大成 9 行红色
   "Cancelled: parallel tool call", 看起来像系统全面崩坏, 实际只有一处坏路径。

## 工程师介入动作
- 失误 1: soft reset 拆开提交回索引 → restore --staged 踢掉他人目录 → 仅暂存自己的 rename → 重新提交;
  事后用 `git show HEAD --name-status` 核对提交只含自有文件。
- 失误 2: 改为顺序执行命令、避免大批量并行、临时文件一律写仓库内或 `$env:TEMP` 而非 `/tmp`。

## 应沉淀的上下文或规则
- **共享工作树禁用目录级 `git add -A <dir>` / `git add .`**: 始终显式列出自己处理过的文件路径,
  或归档时只 `git add` 那一个被移动的具体任务目录; `-A`/`.` 会连带同目录下他人的 untracked 旁支
  (本仓库多 AI agent 同时在主分支工作, 见 VERSION_MANAGEMENT)。提交前必须 `git diff --cached --name-status`
  核对 staged 集合, 确认无他人文件 (不变量 11)。
- **撤销"误纳入"的标准无损组合**: `git reset --soft HEAD~1` 把提交拆回索引, 再
  `git restore --staged <不属于自己的路径>` 逐个踢出, 内容零丢失; 切勿用 `reset --hard` 或
  `checkout` (会损毁他人 untracked/working-tree 改动)。
- **Windows + 顺序执行的 shell 纪律**: 临时文件路径用仓库内相对路径或 `$env:TEMP`, 绝不用 `/tmp`
  (Windows 解析为 `D:\tmp\`, 通常不存在); 倾向顺序执行或小批量, 避免一个坏命令把整批并行调用
  连带 Cancel, 制造"满屏报错"的假象与排错噪音。
