# 工程摩擦记录

> 关联: GH-110 P4.6 (流式扫描进度), 修复提交 3efd9bcc

## 发生阶段
3.0-implement (main→renderer 流式状态推送)

## 现象
P4.6 给扫描加了 `assets:progress` 事件流 (webContents.send) 实时推 status+partial。
上线后应用一打开**一致性地**卡在"扫描中… 0/1"(deriving 阶段), 但数据其实已扫完
(弹层显示已扫 312 项), 切换作用域后 loading 才消失。即: 扫描已完成、产出正确,
但渲染层 status 卡在 scanning —— 是 UI 状态竞态, 不是扫描问题。

## 工程师介入动作
定位为 **微任务/宏任务投递顺序竞态**:
- `refresh({wait:true})` 的 IPC invoke 回复以 **Promise 微任务** 落地 status=ready;
- 而扫描末尾那条 `assets:progress`(deriving, scanning)经 `webContents.send` 以
  **宏任务**(消息事件)投递。
- 微任务先于下一个宏任务执行 → ready 先落, 随后尾随的 scanning 宏任务把它覆盖回
  scanning, 且此后无新事件 → 一致性卡死。
修复: 让 runtime 在扫描**终态**(ready/error)时也经同一 progress 通道补发一条终态
事件。同通道事件保序, 末条必为终态, 消除竞态 (renderer 的 applyAssetProgress 最后
收到 ready)。

## 应沉淀的上下文或规则
- **同一份状态若同时经 IPC invoke 回复 (微任务) 和 webContents.send 事件 (宏任务)
  两条通道下发, 不能假定二者到达顺序。** 微任务恒先于宏任务, 故"回复落终态 + 事件
  补中间态"会被中间态覆盖。
- 规则: 推送式实时状态通道, **必须在终态也经同一事件通道补发一次**, 让该通道自身
  末条消息权威; 不要依赖另一条通道(invoke 回复)兜底终态。
- 等价地, 渲染层也可对"已终态 → scanning"做防回退, 但需 scan 序列号区分新扫描;
  补发终态更简单且无需额外字段, 优先此法。
- 验收瞬态态务必冷重启实测 (见 [[20260607-4.0-verify-scanning-state-screenshot-cold-restart]])。

## 建议的流程改进
(由 harness-5.1-friction 消费) 任何"主进程 push 实时状态 + invoke 拉取兜底"的双通道
模式, 在 design/implement checklist 增一条: 终态必须经 push 通道补发, 并加单测断言
"最后一条 push 事件为终态"。
