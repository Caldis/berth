## 发生阶段

GH-100 标签筛选后续迭代 (折叠浏览态) 的提交推送与 CI 等待。

## 现象

1. **共享单仓库的 push 会替你推送**: 多个 Agent 共用同一个本地仓库工作区。我本地 `git commit` 出 `4dab3aa` 后并未自己 `git push`, 但另一个 Agent 的 `git push origin master` 把整条 master (含我的 `4dab3aa`) 一起推上了远端。`git log origin/master..HEAD` 随即为空, `origin/master == HEAD`。结论: "我没推" ≠ "我的提交没上远端"。
2. **CI 在我的 SHA 上红, 但红点不是我的**: `pnpm harness:ci:wait --sha 4dab3aa` 失败, 失败用例是 `tests/renderer/hooks-lifecycle-view.test.tsx` (以及同类 `category-jump-nav.test.tsx`) 的 `berth-page-gutter` → `berth-page-top-offset` 断言。`git log -- <file>` 显示这两个文件最近由 `863d026 / df6d84d` (另一 Agent 的 GH-99 header block 重构) 改动 —— 组件已提交, 对应测试修订仍在该 Agent 的工作区**未提交**, 于是推上去的状态是**瞬态红**。我的 `4dab3aa` 经 `git show --stat` 证明只动了 `memory-view.tsx` + 两个 i18n + `memory-view.test.tsx`, 与红点无关。

## 工程师介入动作

- 用 `git rev-parse HEAD origin/master` + `git branch -r --contains <sha>` 确认我的提交是否已在远端。
- 用 `git show --stat <my-sha>` 自证我的提交未触及失败文件; 用 `git log -3 -- <failing-test-file>` 定位真正引入红点的提交与作者任务 (GH-99)。
- **不修**失败的 `hooks-lifecycle-view.test.tsx` / `category-jump-nav.test.tsx`: 它们正被 GH-99 Agent 实时编辑 (在未提交集合里), 改动它们会 clobber/冲突其在途工作, 违背"写操作限定在自己文件范围"。
- 如实汇报: 本增量本地全绿且 CI 红点为外部, 不冒充"CI 全绿完成"。

## 应沉淀的上下文或规则

- **CI 红的归因必须落到文件级**: `harness:check` 可 `--work` 收窄到自己任务目录, 但 GitHub CI 跑整棵树、无法 scope。判断红灯是否属于自己, 唯一可靠依据是 `git show --stat <sha>` (我的提交改了哪些文件) + `git log -- <failing-file>` (谁最近改了失败文件), 不能凭"红了就先停我的活"或"红了就去修"。
- **红点属于他人在途提交时, 既不背锅也不越界修**: 另一 Agent 提交了组件却把对应测试修订留在工作区未提交 → 共享分支瞬态红。这种红由该 Agent 收口, 我只汇报、不触碰其文件; 这与 `git push` 会替所有人推送叠加, 容易让自己的绿增量"看起来"骑在红基线上。
- **推送前若可选, 先 `ci:wait` 确认脚下基线绿再叠提交** (本会话归档时对 `e2e4815` 即如此); 但共享仓库里他人可能抢先 push 带走你的提交, 该前置并不总能生效, 故 file-stat 自证是兜底。
