# 工程摩擦记录

## 发生阶段

GH-99 (header 块布局重构) `harness-4.0-verify` 消费 GitHub Actions run 结果时。

## 现象

为确认 CI run 成功, 运行:

```bash
gh run watch <id> --exit-status 2>&1 | tail -6; echo "=== exit: $? ==="
```

输出 `exit: 0`, 误判为 run 成功。实际 `gh run view <id> --json conclusion` 显示 `conclusion: failure`。

根因: bash 里 `$?` 取的是**管道最后一个命令** (`tail`) 的退出码, 不是 `gh run watch` 的退出码。`gh run watch --exit-status` 在 run 失败时本会返回非零, 但被 `| tail` 吞掉, `$?` 永远是 `tail` 的 0。于是把"失败的 CI"读成了"成功"。

这直接威胁 verify 阶段 "主 Agent 必须消费成功结果后才能推进" 的不变量: 一个被管道掩盖的失败可能让人误判 CI 绿、错误地推进 archive。

(本例中真正的红灯来自另一 Agent 的 `df6d84d "Remove hooks recovery center UI"` 回归, 非当前任务; 但若不复核 conclusion, 会误以为分支健康。)

## 工程师介入动作

- 用 `gh run view <id> --json status,conclusion,headSha,displayTitle` 复核, 才发现 `conclusion: failure`。

## 应沉淀的上下文或规则

- **消费命令退出码时, 禁止把要判定的命令接 `| tail`/`| head`/`| grep` 后再读 `$?`** —— `$?` 反映的是管道末端命令, 不是上游。
- CI 结果判定以 **`gh run view <id> --json conclusion`** 的 `conclusion` 字段为准 (`success`/`failure`/`cancelled`), 不只看 `gh run watch` 的退出码, 更不能看管道后的 `$?`。
- 必须读上游退出码时: 用 `${PIPESTATUS[0]}` (bash), 或 `set -o pipefail`, 或不接管道单独运行该命令再读 `$?`。
- 项目封装的 `pnpm harness:ci:wait -- --sha <full-sha>` / `harness:ci:baseline` 内部已按 conclusion 判定, 优先用它们而非手搓 `gh run watch | tail`。

## 建议的流程改进
(由 harness-5.1-friction 消费)

verify / 推送后等待 CI 的标准动作固定为: 优先 `pnpm harness:ci:wait -- --sha <full-sha>`; 需手动查时用 `gh run view --json conclusion` 读 conclusion 字段, 不用 `gh run watch | tail` + `$?` 判定成败。涉及退出码的命令一律不接管道后读 `$?`。
