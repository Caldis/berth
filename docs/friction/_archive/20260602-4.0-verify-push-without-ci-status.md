## 发生阶段

4.0-verify, 关联 task_id GH-35。

## 现象

执行 GH-31、GH-32、GH-33 期间, 每次 push 前只看了本地检查和 GitHub Project 状态, 没有检查 GitHub Actions 的真实任务状态。master 上后续出现多次 CI failure, 但仍继续推送新提交。

## 工程师介入动作

用户指出: “你忽略了 github action 的任务状态，我们中间有非常多 ci 都失败了”，并要求把 CI 状态作为 push 条件: “你需要确保本地测试用例通过且不会影响 ci 的情况下再 push”。

## 应沉淀的上下文或规则

push 不是只看本地检查。完成本地检查后, 还要检查远端 CI:

- push 前查看当前 branch 最新 GitHub Actions 状态。
- 如果 master 最新 CI 已经失败, 且失败可能来自当前会话的提交, 停止新功能推进, 先修 CI。
- push 后等待新 SHA 对应 CI run 完成; 如失败, 立即进入 CI 修复, 不继续做新功能。

## 建议的流程改进

更新 harness workflow:

- `verify` 阶段增加 GitHub Actions 状态检查。
- `commit/push` 规则增加 push 前后 CI gate。
- CI 修复型提交可以在远端已红时 push, 但必须说明它是修复红灯的提交, 并在 push 后等待结果。
