## 发生阶段

implement

## 现象

用户要求修复侧边栏 `配置` 下 `指令` / `能力` 菜单间距不一致问题。该任务可以被视为小改动豁免: 影响范围明确, 实现改动集中在 `sidebar.tsx`, 可用标准门禁和一条 e2e 回归验证。

实际摩擦点不是“使用豁免”, 而是 Agent 没有在实施前主动说明豁免判断, 也没有向用户申请确认, 直接进入了豁免流程。

## 工程师介入动作

用户追问“为什么本次没有走 harness 流程”, 随后澄清: 小改动豁免本身合理, 但 Agent 应主动声明“这是小改动, 申请豁免 harness”, 等用户确认后再直接处理。

## 应沉淀的上下文或规则

小改动豁免只适用于影响范围清楚、实现集中、标准门禁即可验收、无需新建任务态协调的修改。是否触碰测试文件不是唯一判据: 为小修复补一条局部回归测试, 仍可属于小改动豁免。

关键要求是流程透明: 在不走 harness 前, Agent 必须先声明豁免依据并向用户申请确认。用户确认后, 再直接改代码和跑门禁。

## 建议的流程改进

在实施前做一次明确的 harness 入口判定并显式沟通:

- 只读检查可以不建任务态。
- 用户追加“请修复”后, 若判断为小改动, 先说明: “这是小改动豁免候选, 理由是 ...; 是否同意不走 harness 直接修?”
- 用户确认后再实施。
- 若实施中发现影响面超出声明范围, 停下重新申请或切入 harness。
