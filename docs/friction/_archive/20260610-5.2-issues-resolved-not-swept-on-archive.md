# 工程摩擦记录

## 发生阶段

`harness-5.2-issues` 全量收敛 22 项 active issue (2026-06-10, 关联 GH-113/GH-110 归档)。

## 现象

一批 issue 的修复**早已落 commit 并随 work 归档**, 但对应 `docs/issues/` 条目从未移入 `resolved/`, 长期滞留 active, 虚高待办计数、误导后续 Agent 以为还没做。本会话单轮就发现 7 例:

- GH-113 派生: makeid-nondeterministic / global-shallow-conventions-only / scope-filter-project-inheritance (内容已写 RESOLVED, 仍在 active)。
- GH-110 派生: session-error-channel (2b90b7c1) / file-viewer-double-window-controls (604d20b4) / chip-primary-flat-color (91a6cad4) — 文件尾部都写了 "状态: RESOLVED" + commit, 但没 `git mv` 到 resolved/。
- usage-tooltip-test-flaky: 修复在 GH-110 `33751ce5` (per-test 15s timeout), issue 却仍 active。

根因: `5.0-archive` 把"关联 issue 的清理"列为**可选提醒** (`ARCHIVE_BACKLOG_REMINDER`), 实际从不在归档当轮执行; 而 `5.2-issues` 又是低频手动触发。两个动作之间, "已修复 issue → resolved/" 这一步无人负责, 于是稳定泄漏。

## 工程师介入动作

- 收敛时不信任 issue 自述的 "RESOLVED" 字样, 逐个回真源核验: `git cat-file -t <commit>` 确认 commit 存在 + Read 代码/测试确认行为已改 (如 scope.ts owner-tagging + scope.test.ts:74-77; usage-tooltip 的 `git show HEAD:<test>` 含 15000)。
- 核验通过的 `git mv` 到 `resolved/` 并补完成日期/解决说明; harness:check 通过后提交。
- 全量分析 active 时用 Explore 子代理按主题簇并行摘要, 才高效捞出"内容已 RESOLVED 但滞留"的隐藏项 (单看文件名看不出)。

## 应沉淀的上下文或规则

- **"修复落地" 与 "issue 移入 resolved/" 是两件事, 后者极易漏。** 任一 work 在 implement/verify 修了某个 `docs/issues/` 条目, 归档当轮就应把该 issue `git mv` 到 `resolved/` 并补解决说明 — 不要留给将来某次 5.2-issues。
- **收敛已修复 issue 必须证据先于归档**: 不凭 issue 内 "RESOLVED" 字样, 回 commit 存在性 + 代码/测试真源确认; 防止把"声称修复"误判为"已修复"。
- 全量 issue 分析时, 已修复但滞留的项**无法从文件名识别**, 必须读内容 (可并行 Explore 摘要); 否则只会处理新建项、漏掉历史泄漏。

## 建议的流程改进
(由 harness-5.1-friction 消费)

在 `.agents/workflow/5.0-archive.md` 把"关联 issue 收敛"从可选提醒升级为**归档清单硬项**: 归档前列出本 work 在 implement/verify 修复或取代的 `docs/issues/` 条目, 当轮逐个补解决说明 + `git mv` 到 `resolved/` (含 commit 引用), 与 INDEX phase=archive 同批提交; harness-check 可增一条软校验 (work INDEX 若声明 resolved 了某 issue, 该 issue 应在 resolved/)。如此 5.2-issues 退化为兜底巡检而非主清道夫。
