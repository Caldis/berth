# 工程摩擦记录

> GH-121 B2 (2026-06-12)。

## 发生阶段
3.0-implement — 物理迁移 `src/main/engine` 等目录进包时。

## 现象
用户 `pnpm dev --watch` (electron-vite) 正在运行, 其 watcher 持有被迁移目录的句柄: Windows 下**目录级** `git mv src/main/engine packages/...` 直接 `Permission denied`; 且第一个 fatal 后命令链中 `;` 分隔的后续 mv 在目标父目录未建时报 "No such file or directory" 混淆归因。

## 工程师介入动作
- `Get-CimInstance Win32_Process` 区分出锁是**用户 dev** (electron-vite + `electron.exe .` 无 `--berth-agent-instance`), 按规则不杀不清。
- 探测发现**文件级** `git mv` 不受目录句柄锁影响 → 改为逐文件循环 mv (保持相对结构), 53 文件全部成功; 旧空目录壳留待 dev 停止后清理。
- 附带影响: 用户 dev 以旧 config + 已迁走的 worker 入口继续 watch, rebuild 失败并清掉 `out/main/asset-worker.js`, 致产物钉测红 — `pnpm build` (新 config) 重建即恢复; 用户 dev 需自行重启才能用新 config (汇报中告知)。

## 应沉淀的上下文或规则
- 共享工作区 + Windows: **目录级 rename 被任何 watcher (用户 dev / e2e 残留) 锁死, 文件级 rename 不受影响**。物理迁移目录前先 `Get-CimInstance` 查 berth 进程; 有用户 dev 在跑时直接用逐文件 mv 方案, 不浪费一轮目录级尝试。
- 迁移期间产物钉测 (worker-artifact) 红优先怀疑 "watch rebuild 用旧 config 清了产物", 重 build 验证, 不当回归追。

## 建议的流程改进
(由 harness-5.1-friction 消费) 可在 3.0-implement 的"实现期跨切面约束"追加一条: 目录级物理迁移前检查活动 watcher 进程, Windows 下默认文件级迁移。
