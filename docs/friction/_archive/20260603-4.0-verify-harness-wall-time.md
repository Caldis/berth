# 工程摩擦记录

## 发生阶段

4.0-verify / archive 前后, GH-88 文档资产迁移任务。

## 现象

用户反馈 harness 流程体感很慢。结合本轮实际命令耗时, 慢主要来自强制门禁和远端同步:

- 本地 `pnpm harness:prepush` 约 27 秒, 其中 `pnpm test` 的 Vitest 汇总耗时约 16 秒, lint/typecheck 约 9-10 秒, `harness:check` 本身小于 1 秒。
- 每次推送后的 `pnpm harness:ci:wait` 约 3 分钟, Windows job 是主耗时, 因为包含 install、lint、typecheck、test、harness:check、build、e2e。
- `node scripts/harness-projects.mjs ensure ...` 单次约 28 秒, 属 GitHub Project 网络同步。
- 官网子项目首次 `pnpm --dir website install --frozen-lockfile` 约 10 秒; `pnpm --dir website build` 约 5 秒。
- 创建 Issue、写 00/01/02/03/INDEX 与 Project 字段同步会增加固定操作开销, 小型 docs 变更也会承担这套成本。
- GH-90 导航任务中, 用户明确反馈 CI 验收太费时间, 要求当前会话后续跳过 CI wait; 因此后续只保留本地门禁与必要推送, 不再等待 GitHub Actions 完成。

## 工程师介入动作

已记录实际耗时区间, 并在最终回复中区分本地测试、远端 CI、GitHub Project 与任务态文档四类耗时来源。
GH-90 后续执行遵循用户当前会话偏好: 新增提交不等待远端 CI。

## 应沉淀的上下文或规则

harness 慢不是单点命令慢, 而是多个固定门禁串行叠加。小范围 docs/website 改动中, `harness:check` 很快, 真正耗时的是全量 prepush、CI wait 和 Project 同步。

## 建议的流程改进

- 为纯 docs / website / workflow path-filter 任务增加明确的 lighter verify profile, 用目标构建与 `harness:check` 作为本地必跑项, 把全量 Vitest 留给 CI 或 archive 前总检。
- 将 GitHub Project ensure/check 合并到一个步骤, 或只在 INDEX debt / phase / project 字段变化后运行。
- CI 分层: docs-only / website-only 变更不必跑 Electron Windows e2e; Pages workflow 可单独验证 website build。
- 在 harness 脚本中输出阶段耗时摘要, 让慢点可观测。
