## 现象
- god-pages 改动**纯 renderer** (session-detail/capabilities/instructions 页面纯函数提取 + 3 lib), 本地全量门禁全绿 (typecheck node/web/test + lint + 1279 test + harness:check), 前 3 个 work (GH-142/143 + BUG) CI 均 success。

- 易盲目按不变量 11 "CI failure 来自当前会话提交 → 回 implement" 去回退或改产品码。

## 工程师介入动作 (归因方法, 未盲目回退)
先做**失败域 vs 改动域**归因 + 重跑确认:
1. **失败域**: `shallowOwners()` 查 `window.api.assets.snapshot()` (主进程 IPC 快照), searchPaths/setProjectScope 同为 IPC — 全不碰 renderer DOM。
2. **改动域**: god-pages 纯改 renderer 页面渲染逻辑 — 与主进程扫描/快照**不相交**, 逻辑上不可能引入此失败。
3. **相关扫描改动核查**: 失败路径 shallow conventions (`shallow-conventions.ts`) **不依赖** GH-142 的 scan-ignore/buildScanIgnore; filterExcludedPaths 兜底对空 excludePaths 是 identity — GH-142/143 (真改扫描) 未触及 shallow 路径。
4. **失败特征**: poll **timeout** (worker→IPC→scope 全链路 5s) 而非断言值错 — 时序 flaky 特征。
5. **重跑确认**: `gh run rerun <run-id> --failed` 重跑同 commit macos job → success。同 commit 唯一变量是重跑 = flaky 铁证。

## 应沉淀的上下文或规则
- CI 红 (尤其 macos/windows e2e 的 poll/wait **timeout** 类) 先做**失败域 vs 改动域**归因, 再决定是否回 implement:
  - 失败 e2e 查的层 (主进程 IPC / 渲染 DOM / 引擎) 与当前改动碰的层**不相交** → 改动逻辑上不可能引入 → 默认 flaky。
  - 失败是 poll/wait **timeout** (非断言值错) → 时序 flaky 优先。
  - 核查"相关"改动是否真触及失败代码路径 (import 链 / 函数调用), 不因"改了扫描"就认定所有扫描 e2e 红是自己引入。
- 确认手段: `gh run rerun <run-id> --failed` 重跑同 commit 失败 job; 同 commit 重跑绿 = flaky。不改一行就盲目回退。
- renderer-only 改动 + 全量 unit/renderer (1279) + 组件回归绿时, 主进程 IPC / 扫描 e2e 的偶发 timeout 几乎必为 flaky。
