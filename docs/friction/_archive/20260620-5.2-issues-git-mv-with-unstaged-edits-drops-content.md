# 工程摩擦记录

> task: 批量收敛 issue (close → 移入 resolved/), 给每个 issue 先 Edit 追加 "## 收口" 解决记录, 再 `git mv` 到 resolved/

## 发生阶段
5.2-issues (issue 关闭簿记) — 适用于任何 "改文件内容 + 同提交移动该文件" 的操作

## 现象
对 4 个 issue 文件先 `Edit` 追加 "## 收口" 正文 (工作树未暂存改动), 紧接着 `git mv docs/issues/X.md docs/issues/resolved/`, 然后一次 `git commit`。
提交后 `git diff --cached --stat` 显示 **R100 (100% 纯重命名)**, "0 insertions / 0 deletions" —— **追加的正文没进提交**。`git mv` 把"重命名"暂存为从旧路径**已提交 blob** 到新路径, 而 Edit 的内容改动仍以**未暂存**形式挂在新路径上。结果: 文件移动成功, 但解决记录正文丢失 (只在工作树, 未入库)。下一次 `git status` 才暴露 `M resolved/*.md` 一堆未暂存修改。

## 工程师介入动作
1. **收尾必查 `git status`**: 本批靠收尾审计发现 4 个 `M resolved/*.md` 未暂存, `git diff` 确认正是丢失的 "## 收口" 正文, 补一次提交补回。
2. **修正操作序**: 之后的关闭批改为 `git mv` **之后**对新路径 `git add` 一次 (re-stage 携带工作树内容), 提交前 `git diff --cached` 看到 R089/R073 (相似度 <100% = 内容确实进了) 而非 R100, 确认正文已暂存。

## 应沉淀的上下文或规则
- **`git mv <有未暂存编辑的文件>` 只暂存重命名 (旧 blob→新路径), 不携带未暂存的内容改动**。"改内容 + 移动" 同提交时, 必须二者之一:
  - 先 `git add <旧路径>` (暂存内容) 再 `git mv`; 或
  - `git mv` 之后再 `git add <新路径>` (re-stage 携带工作树内容)。
- **判据**: 提交前 `git diff --cached --stat` 若对一个"应有内容改动"的移动显示 **R100 / 0 insertions**, 即内容没进暂存 —— 立即补 `git add`。R100 对纯移动正常, 对"移动+改内容"是 bug 信号。
- 呼应既有暂存纪律 (只 `git add` 自己文件 + `git diff --cached` 核对): 本条补的是"移动+改内容场景下, `git diff --cached` 还要核对**内容是否真进了暂存**, 不只核对文件集"。
