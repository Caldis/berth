# 工程摩擦记录

## 发生阶段
optimization (执行 navigator.platform 弃用替换这一小改动时)。

## 现象
[[new-harness-entry-no-mandatory-trigger]] 引入的"何时进入 (强制)"豁免项仅覆盖"单行/拼写/纯文案注释, 且无需验收"。但 navigator.platform → userAgentData 这类弃用替换: 改动小 (1 新文件 + 同文件 2 处), 单一关注点, 标准门禁即可验收, 却**需要验收**, 故不落入原豁免。结果对一个 2 行级修复, 要么套全 harness (5 文档 + 任务目录 + gh, 明显过重), 要么违反自己刚提交的规则。规则在"过重"与"违规"之间无第三条路。

## 工程师介入动作
按"小改动 + 门禁"直接处理 (新建 lib/platform.ts + 单测, sidebar 3 处替换, typecheck/lint/test 全绿), 并加宽豁免规则使其自洽。

## 应沉淀的上下文或规则
1. 豁免标准应以"改动规模 + 是否需跨文件分析/人工澄清"为轴, 而非以"是否需要验收"为轴 — 任何代码改动都需要门禁验收, 以此为豁免条件等于禁止一切小改动豁免。
2. 健康的流程需要"小改动快车道": 单一文件·单一关注点·标准门禁即可验收·无需跨文件根因分析或人工意图澄清的改动, 直接处理 + 跑门禁 (含可测试性), 不建任务态。

## 建议的流程改进 (已落地)
1. AGENTS.md 与 .agents/README.md 的"何时进入"豁免项从"单行/纯文案"加宽为上述"小改动快车道"。
2. 仍保留可测试性与门禁为硬要求: 豁免的是任务目录/文档/gh 仪式, 不豁免验证。
