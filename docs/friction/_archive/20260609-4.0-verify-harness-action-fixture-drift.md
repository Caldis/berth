## 发生阶段
3.0-implement 提交 harness `0.2-sync` 步骤时埋下, 4.0-verify 跑 CI 时暴露。

## 现象
- 加 `0.2-sync` 到 `WORKFLOW_ACTIONS` + 写 `.agents/workflow/0.2-sync.md` 后, 本地 `pnpm harness:check` 通过 → 直接提交推送; 但 CI 红: `tests/harness/check.test.ts` 的 `checkWorkflowSources`/`checkFriction` 两个测试**硬编码**了一份 10-action 的 fixture 列表, 没含 `0.2-sync` → `checkWorkflowSources` 在 fixture 目录报"缺 0.2-sync.md"。
- 根因: `harness:check` 校验的是真实 `.agents/workflow/` (含新写的 `0.2-sync.md`, 故过); 而 harness 单测用临时 fixture 目录 + **硬编码 action 列表**, 与 `ACTION_IDS` 静默分叉。只跑 `harness:check` 检不出, 漏跑全量 `pnpm test` 直接推送 = friction `20260607` "陈旧绿" 的复发。

## 应沉淀的上下文或规则
- **`harness:check` ≠ 全量验证**: 改 `WORKFLOW_ACTIONS` / harness 体系结构后, `harness:check` 过**不代表** harness 单测过 (单测 fixture 可能与 `ACTION_IDS` drift)。**改 harness 体系后必须跑全量 `pnpm test`** (至少 `tests/harness`), 不能只 `harness:check`。
- **根治 (已落地)**: `tests/harness/check.test.ts` 两处硬编码 action 列表改为派生自 `ACTION_IDS` (单一真源), 测试名去掉硬编码数字 ("全部 10 个" → "全部"), 下次加 action 自动覆盖, 杜绝 fixture drift。
- 关联 friction `20260607` (提交前对最终 staged 跑全量 lint+typecheck+test)。

## 建议的流程改进
- 改 `scripts/harness-lib.mjs` 的 `WORKFLOW_ACTIONS` 后, 提交前门禁必须含 `pnpm test` (或至少 `tests/harness`), 不止 `harness:check`。
- 测试 fixture 凡需枚举"全部 action / 全部 type / 全部 scope"等与库常量一一对应的集合, 一律派生自库导出的单一真源, 禁止再抄一份硬编码列表。
