# 工程摩擦记录

## 发生阶段
optimization

## 现象
用户指出: 当用户提出改善意见时, agent 不应直接假设一定要写入摩擦记录或修改规则。应先判断这是不是代价非常小的修正; 若是, 再询问用户希望把它沉淀为 friction 并改规则, 还是只作为当前会话行为校准直接调整。

## 工程师介入动作
先确认这条反馈属于低成本流程治理修正, 再向用户询问处理方式。用户选择“落到摩擦记录并改 harness 规则”后, 将该判断分支写入 `.agents/workflow/_shared.md`。

## 应沉淀的上下文或规则
用户提出流程改善意见时, 先做低成本判断。若修正代价非常小, 不要直接写文件; 先询问记录方式: 落 friction 并改规则, 或只在当前会话调整行为。

## 建议的流程改进
后续处理用户纠正/偏好时, 在执行前增加一步轻量分类: 低成本行为校准、需要沉淀的 harness 规则、产品 bug/功能问题。只有用户确认要沉淀时, 才写 friction 或规则文件。
