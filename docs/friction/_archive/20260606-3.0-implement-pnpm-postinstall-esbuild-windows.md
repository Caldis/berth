## 发生阶段
3.0-implement (P1.1 建 pnpm workspace + packages/berth-scan-engine 骨架, 首次 `pnpm install` 引入 workspace)。

## 现象
Windows + pnpm 9 下 `pnpm install` 的**依赖解析与链接全部成功** (workspace 2 projects, packages +16), 但**根 `postinstall`** (`electron-builder install-app-deps`) 失败退出 1:

```
electron-builder ... installing native dependencies arch=x64
⨯ ENOENT: no such file or directory, stat
  'D:\Code\berth\node_modules\.pnpm\node_modules\@esbuild\aix-ppc64'
```

- 根因: esbuild 把所有平台二进制列为 optionalDependencies (`@esbuild/aix-ppc64`、`@esbuild/linux-x64` …), pnpm 在 Windows 只物化 `@esbuild/win32-x64`; electron-builder / @electron/rebuild 在 `install-app-deps` 阶段遍历并 `stat` 这些目录, 命中未物化的平台包即 ENOENT 致命退出。
- esbuild 早已经由根 `vite` 进入依赖树 (且 `vitest` 也经 vite 引入 esbuild), **与本次新增 `tsup` 无关** —— 即把引擎包构建从 tsup 换成 tsc 也不会消除该 esbuild 表面。属**预先存在的 Windows 本地环境摩擦**, 由"重新 install"触发 postinstall 才暴露。

## 工程师介入动作
- 判定该失败**不阻塞开发链路**: 失败发生在 native app-deps 重建 (仅 `electron-builder` 打包需要), 链接已完成。验证 `pnpm --filter @berth/scan-engine test` (3/3 绿)、`typecheck`、`build` (ESM+CJS+dts) 与根 `pnpm typecheck:node` 均通过; 本次 install "reused 1121", 仅新增 16 个与 better-sqlite3 无关的包, 既有 Electron-ABI 的 better-sqlite3 binding 未被改动, `pnpm dev` 不受影响。
- CI 跑在 Linux 干净环境 (`@esbuild/linux-x64` 已物化), 不复现此 Windows 本地问题; 故提交/推送 P1.1 不会因此红 CI。

## 应沉淀的上下文或规则
- Windows 本地重跑 `pnpm install` 时, 若仅做 dev/test/typecheck/build, 可忽略 `electron-builder install-app-deps` 的 esbuild ENOENT (非致命于这些任务)。
- 需要打包 (`pnpm package`/`electron-builder`) 时, 用 `pnpm install --ignore-scripts` 跳过有问题的 postinstall, 再针对性重建原生模块 (better-sqlite3), 而非依赖全量 app-deps 遍历。
- 该现象**不是回归**: 引擎包用 tsup 还是 tsc 不影响 (esbuild 已由 vite/vitest 引入)。评估"换 tsc 去 esbuild"对此无效, 不必为此返工。
- 与 AGENTS.md BUILD_ENV 既有 pnpm 9 / corepack 约束同源, 同属"重装类"环境坑。
