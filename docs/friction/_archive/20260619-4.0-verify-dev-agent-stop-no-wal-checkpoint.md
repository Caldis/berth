# 工程摩擦记录

task_id: GH-140 (冷启动首屏 SWR 验证)

## 发生阶段
4.0-verify — 真跑验证"有持久快照的冷启动" (stale → SWR) 路径。

## 现象
要验证 ensureReady 的 SWR 修复, 需要一个"冷启动 + restorePersistedSnapshot 成功 (status=stale)"的真机场景。直觉做法 `dev:agent start → stop → start 同 id` 制造冷重启失败:
- `dev:agent stop` 用 kill 杀 electron, **不是正常 quit**, 不触发 better-sqlite3 的 WAL checkpoint。
- 主 `berth-index.db` 文件停留在 `user_version=0` + `no such table` (asset/snapshot_meta 数据滞留未 finalize 的 WAL)。
- 下次 `dev:agent start` 打开时 schema 版本不匹配 → `ensureSchema` 走 purge (DROP TABLE) → `restorePersistedSnapshot` 读不到快照 → 冷启动落 **idle (首扫)** 而非 stale。
- CDP 实测得到 `statusBefore:"idle"` + `insightsMs:28777` (走了首扫 await), 一度误判 SWR 修复无效。

附带: 复制 WAL 模式 sqlite 库做只读 sqlite3 查询时, 只 cp 主 `.db` (漏 `-wal`/`-shm`) 会看到 `no such table` / 旧数据 — WAL 未回放。

## 工程师介入动作
- 用用户真实 `berth-index.db` (正常 quit 过, `user_version=1` + envelope + 1319 assets, 完整可 restore) 作为 seed。
- `PRAGMA wal_checkpoint(TRUNCATE)` 把数据落进主文件后, 复制到 agent profileDir/berth-index.db (删掉旧 `-wal`/`-shm`), 再 `dev:agent start`。
- 冷启动即走 restore → `statusBefore:"stale"`, `insightsMs:21` (SWR 生效)。

## 应沉淀的上下文或规则
- 验证依赖"已持久化冷启动状态"的功能 (SWR / restore / snapshot 缓存 / 冷启动) 时, **不能靠 `dev:agent stop→start` 制造"有快照的冷启动"** — stop=kill 不 checkpoint WAL, 下次启动会 purge 走 idle。
- 正确做法: seed 一个 checkpoint 完整的 DB (`PRAGMA wal_checkpoint(TRUNCATE)` 后复制, 或直接用正常 quit 过的真实 DB) 到 agent profileDir, 再 start。
- 诊断"DB 文件有大小但 restore 失败/查无表": 先查主文件 `PRAGMA user_version` (0 = WAL 未 checkpoint) 与是否漏复制 `-wal`/`-shm`。
- 只读查询 WAL 模式 sqlite 副本必须 cp `db` + `-wal` + `-shm` 三件套。
