# 前端项目缺少前置界面质量门槛

## 发生阶段

5.1-friction

## 现象

当前 workflow 对 UI 的要求主要集中在 verify 阶段: 启动应用、截图、走通交互, 并要求 UI 改动用 `frontend-design` 指导视觉判断。`3.1-polish` 也会检查交互和视觉优化点, 但它是可选阶段。也就是说, 对前端项目来说, 界面设计风格是否合理、交互是否清楚、状态是否完整, 没有在 Explore / Design 阶段变成必须写入的验收条件。

这会导致两类问题: 一是实现前没有明确的 taste / interaction 目标, 只能在 verify 或用户截图反馈时补救; 二是 polish 容易被误当成“补齐基本 UI 质量”的阶段, 而它本应只做可选加深检查。

## 工程师介入动作

用户指出 berth 是前端项目, 需要确认流程里是否有关于用户界面设计风格、交互优化、门禁、验收条件或 taste 指引的规则。检查后确认现有规则有后置视觉验收, 但缺少前置界面质量与交互验收门。

## 应沉淀的上下文或规则

前端或 UI 相关任务必须在 Explore 记录现有页面结构、设计系统用法、信息密度、主要用户路径、可见状态、交互反馈、响应式和可访问性风险。Design 必须写清布局层级、组件选择、状态覆盖、交互反馈、响应式、可访问性、文案/i18n 和验收方式。Verify 必须逐条实测这些项。Polish 只能加深检查, 不能替代 Design 阶段的界面方案。

## 建议的流程改进

- 在 `_shared.md` 增加前端 / UI 任务的界面质量与交互验收不变量。
- 在 `1.0-explore.md`, `2.0-design.md`, `4.0-verify.md` 加入对应步骤。
- 在 `docs/works/_template/01-ANALYSIS.md`, `02-SPEC.md`, `03-PLAN.md` 加入模板项。
- 在 `harness:check` 中检查关键 playbook 和模板包含 `界面质量与交互验收`。
