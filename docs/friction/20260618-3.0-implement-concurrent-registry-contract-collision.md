## 发生阶段
3.0-implement (向可枚举注册契约新增条目时, 另一 agent 同时在改同一批共享文件)

## 现象
准备给仪表盘加 `per-project-activity` widget, 第一步 Edit `widget-types.ts` 即报
`File has been modified since read`。重读发现另一并发 agent 已把 `project-allocation` 加进
WidgetId union —— **撞维度** (都在做"项目维度") **且撞文件**。任何新 widget 都要改同一批 6 个
共享契约文件 (widget-catalog / widget-types / widget-registry + en/zh.json + dashboard-layout.test),
两个 agent 同时编辑必然 last-writer-wins 互相覆盖。`git status` 显示对方改动**未提交**, 即
mid-flight, 共享文件正不稳定。若当时硬改, 会污染对方在途工作或被其覆盖。

## 工程师介入动作
1. **撞前先 grep 占用**: 落第一笔写之前先 `grep -rn '<new-id>|<dimension-keyword>' src/ tests/`
   确认维度/id/order 没被并发占用。本次因此换维度 (项目→模型趋势, 堆叠面积新形态), 不重复劳动。
2. **先做独占层, 与共享契约解耦**: 新维度需要新引擎聚合 (`buildModelTrend`), 这部分只落在我独占的
   engine 文件 (activity-insights / insights 类型 / 单测), 与对方的 usage-based widget 零重叠 →
   先建 + 全绿 + **提交** (commit 85dbec3), 把可立即交付的价值锁定, 不被共享文件竞态阻塞。
3. **等共享文件 settle 再做注册**: 轮询 `git status`, 待对方 `project-allocation` 提交 (2a7d986)、
   工作树 clean 后, 才动那 6 个共享文件; 注册时按对方落定的 order 13 续到 order 14。
4. **每个共享文件改前即时重读**: 把 Edit 的"file modified since read"当**竞态探测器** —— 命中就
   重读再改, 不盲目 retry 旧 old_string。
5. 暂存只 `git add` 自己的 model-trend 文件 + `git diff --cached` 核对, 绝不带入对方/fork 的文件。

## 应沉淀的上下文或规则
- **向"可枚举注册契约"(union 类型 / catalog map / registry / i18n key 表 / 计数断言)并发新增条目,
  是本仓的高频撞车点**: 这类契约天然要求每个新成员同时改同一组中心文件, 两个 agent 并行加成员 = 必撞。
- **操作序列 (并发加成员时照此走)**:
  ① 写第一笔前 grep 新 id / 维度关键字, 确认未被占用 (撞了就换维度或换 id, 别重复造同一个);
  ② 把不碰共享契约的**独占层** (引擎/纯函数/类型/单测) 先建先提交, 解耦交付;
  ③ 待对方对共享文件的改动**已提交且工作树 clean** 再做注册编辑, 顺着已落定的序号续;
  ④ 每个共享文件改前即时重读, 用"file modified"当竞态信号。
- 呼应既有 (已归档) 的 shared-tree 暂存纪律: 写操作限定自己文件范围 + `git diff --cached` 核对;
  本条补的是"**何时**能安全动共享文件"的时序, 不只是"暂存哪些"。
