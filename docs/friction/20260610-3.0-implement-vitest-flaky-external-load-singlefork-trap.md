# 工程摩擦记录

> GH-115 T0 门禁期间, 全量 vitest 两次运行失败集漂移 (1 失败 → 5 失败, 文件互不相同), 排查耗 3 轮。

## 发生阶段
3.0-implement (GH-115 T0 门禁)。

## 现象
1. 本机其他项目高负载 (foody-admin umi dev ~70% CPU + metro workers) 时, 全量 vitest 的长耗时渲染测试 (settings-agent-plugins / sessions-pages / hooks-lifecycle-view / usage-tooltip-label) 随机超时, 失败集每次运行不同, 单文件 duration 涨到 22-76s (正常 6.5s)。
2. 二次排查时用 `--pool=forks --poolOptions.forks.singleFork` 串行复跑 4 个文件, sessions-pages 出现 10+ 个新失败 — 这是复跑方式自己制造的假失败: singleFork 让多个测试文件共享一个进程, renderer hooks 的 module-level SWR 缓存 (sessionListInFlight 等 5 套) 跨文件泄漏, 文件间互相污染 (即 GH-115 R13 finding `swr-abstraction-reset-coupling` 描述的风险在测试态的实证)。

## 工程师介入动作
无 (Agent 自查), 但浪费两轮后台运行与一轮误判风险。

## 应沉淀的上下文或规则
- **判定法**: 全量 vitest 失败集随运行漂移 + 失败用例 duration 显著膨胀 → 先 `ps aux` 查外部负载 (本机常驻 foody-admin/metro), 再用**默认隔离模式**只跑失败文件; 绿即判环境 flaky, 以 CI (干净机器) 为权威门禁, 不阻塞提交。
- **禁止**: 用 `singleFork`/`singleThread` 串行复跑 renderer 测试来"排除并发因素" — 本仓 renderer hooks 有 module-level 缓存, 共进程复跑必产生跨文件污染假失败, 误导根因判断。隔离与负载是两个变量, 复跑只能动负载 (单独跑), 不能动隔离 (合进程)。
- SWR 缓存收敛 (issue renderer-cached-resource-hook) 落地统一 resetAllCachesForTests 后, 此陷阱面会缩小。

## 建议的流程改进
- 4.0-verify / 门禁类 playbook 可加一行: vitest 全量失败时先看失败集是否跨运行稳定; 不稳定先查负载并默认隔离重跑, 不要直接进入逐用例 debug。
