# 工程摩擦记录

## 发生阶段

GH-99 (header 块布局重构) `harness-5.0-archive` 移动任务目录到 `_archive`。

## 现象

archive playbook 的步骤顺序是: step 3 先把 `INDEX.phase` 改为 `archive` (工作树编辑, 未暂存), step 4 再 `git mv docs/works/{task} docs/works/_archive/{task}`。

`git mv` 只把 **index/HEAD 里的 blob** 改名暂存; 此前对 `INDEX.md` 的**未暂存工作树编辑** (phase=archive, 以及 `harness-projects done` 写入的 `item_status: Done`) 不会被带进 rename, 而是停留为新路径上的未暂存修改。`git status` 显示为 `RM`(R=已暂存改名, M=工作树未暂存修改)。

结果: 归档提交的 commit 摘要是 `rename ... (100%)` `0 insertions/0 deletions` —— 归档后的 `INDEX.md` 仍是旧内容 (`phase: verify`, `item_status: In Progress`), phase/Done 编辑丢在工作树未提交。若不自查, 会误以为已正确归档。

## 工程师介入动作

- 自查 commit 摘要发现 `100% rename / 0 insertions`, 与"应有 phase/Done 内容变更"矛盾。
- `git show HEAD:<archive>/INDEX.md | grep phase` 确认提交的是旧内容。
- `git add <archive>/INDEX.md` 后补一次提交, 把 phase=archive / item_status=Done 落库, 再回读确认。

## 应沉淀的上下文或规则

- **`git mv` 不携带被移动文件的未暂存工作树编辑**: 它只 rename index 里的 blob。先编辑后 `git mv` 会把编辑留在新路径的未暂存区。
- archive 收口正确姿势 (二选一):
  - 先 `git mv` 目录, 再编辑新路径下的 `INDEX.phase`, 然后 `git add` 该 INDEX 一并提交; 或
  - 编辑后 `git mv`, 提交前对被移动且改过的文件再 `git add` 一次, 并用 `git diff --cached` 核对内容变更确实在 staged 集合里。
- 归档提交后必做自查: `git show HEAD:<archive-path>/INDEX.md | grep -E '^phase:|item_status:'` 确认 `phase: archive` 且 `item_status: Done`; 不能只看 `rename (100%)` 摘要就放心。

## 建议的流程改进
(由 harness-5.1-friction 消费)

在 `.agents/workflow/5.0-archive.md` step 4/5 补一句: `git mv` 后必须 `git add` 被移动且编辑过的 `INDEX.md` (phase/Done), 并用 `git diff --cached` 确认 phase/item_status 变更在 staged 集合; 提交后 `git show HEAD:<archive>/INDEX.md` 回读 phase=archive / item_status=Done。
