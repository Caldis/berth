## 现象
排查"哪台 Mac 有 Developer ID Application 签名私钥"时绕了多轮、误判:
- 先用 `security find-identity -v -p codesigning` 查 macmini/macbook, 只见 `Apple Development` 证书, 据此判断"两台都没有 Developer ID 私钥", 一度准备让用户**新建一张 Developer ID 证书**(多余的弯路)。
- 用户坚持"两台都设置过, 仔细找", 才改用 `find ~ -name '*.p12'` 全盘搜, 在 macmini `~/Docs/ci-signing/keys/dev-id-app.p12` 找到含私钥的 .p12 + 同目录 `github-macos-codesign.md`(记着 .p12 密码、Apple ID、Team ID、完整流程)。
- 根因: **私钥以 .p12 文件形式存在, 从未导入钥匙串** → `security find-identity` 永远看不到它 (即使不加 `-v`), 但它对 CI 完全可用 (electron-builder 用 CSC_LINK=base64(.p12) 在 runner 上临时导入)。
- 次要绕路: 纠结 Developer ID 证书的 Team ID `N7Z52F27XK` vs Apple Development 的 `BJQ2YFB3HJ`, 把脚本写死 N7Z, 引发用户"从哪学来的"质疑; 实际应自动识别。

## 工程师介入动作
- 用户两次纠正: "你就用 BJ 那个"(误以为开发证书可用)、"我 1000% 确定设置过, 仔细找"(指向文件搜索)。
- 最终用 `~/Docs/ci-signing/keys/dev-id-app.p12` + 文档里的密码, 从本机已登录的 gh 直接 base64 管道设 MAC_CERTS, dry-run 一次签名+公证通过。

## 应沉淀的上下文或规则
1. **排查 macOS 签名身份可用性, 不要只信 `security find-identity`** — 它只反映**钥匙串里**的 cert+key 配对。CI 签名材料常以 **.p12 文件**独立存放 (本仓库: macmini `~/Docs/ci-signing/`)。下结论"没有私钥 / 要新建证书"之前, 先 `find ~ -iname '*.p12'` + 看约定的签名材料目录。已记入用户记忆 `macos-codesign-materials-macmini`。
2. **Apple Development 证书 ≠ 可发布** — 不能用于 Developer ID 分发/公证 (notarize:true 会 CI 失败), 不能拿来"将就"代替 Developer ID。
3. **签名脚本/检查不要写死 Team ID** — 从 `Developer ID Application: NAME (TEAMID)` 自动提取, 兼容任意账号/新证书, 也避免"凭记忆填"的质疑。
4. Berth/bobcorn 复用同一套 Developer ID (Team N7Z52F27XK); 材料与流程文档在 macmini `~/Docs/ci-signing/github-macos-codesign.md`。
