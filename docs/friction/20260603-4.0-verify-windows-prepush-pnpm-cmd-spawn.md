# 工程摩擦记录

## 发生阶段

4.0-verify, GH-91 Hooks 生命周期布局修复提交后的 pre-push 检查。

## 现象

执行 `pnpm harness:prepush` 后, 脚本输出 `harness-prepush: running lint, typecheck, test, harness:check, harness:ci:baseline in parallel`, 随后立即失败为 `spawn EINVAL`。没有进入 lint、typecheck、test 或 harness 检查本身。

## 工程师介入动作

- 直接执行 `node scripts/harness-prepush.mjs`, 稳定复现 `spawn EINVAL`。
- 读取 `scripts/harness-prepush.mjs`, 确认 Windows 分支固定使用 Node `spawn('pnpm.cmd', ...)`。
- 用 Node `spawnSync('pnpm.cmd', ['--version'])` 和完整路径 `C:\Users\mail\AppData\Roaming\npm\pnpm.cmd` 复现 `EINVAL`。
- 用 `cmd.exe /d /s /c pnpm.cmd --version` 验证同一 pnpm 可运行, 输出 `9.15.4`。
- 分别补跑 `pnpm lint`, `pnpm typecheck`, `pnpm test`, `pnpm harness:check`; 本次提交相关本地检查均通过。

## 应沉淀的上下文或规则

在当前 Windows + Node 24 环境下, `harness:prepush` 的失败可能发生在启动 `.cmd` 阶段, 不代表应用代码检查失败。遇到 `spawn EINVAL` 时, 先复现并确认是否为 `pnpm.cmd` spawn 问题; 若是, 需分别运行 pre-push 中的检查项, 并明确记录 `harness:prepush` 本身未通过。

## 建议的流程改进

`scripts/harness-prepush.mjs` 可在 Windows 上改用 `cmd.exe /d /s /c pnpm.cmd <script>` 或增加 fallback。脚本也应把失败任务名和 spawn 参数输出出来, 避免只暴露 `spawn EINVAL`。
