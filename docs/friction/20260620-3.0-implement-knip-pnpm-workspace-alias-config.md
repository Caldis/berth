# 工程摩擦记录

task_id: GH-147 (knip 死代码扫描入 CI)

## 发生阶段
3.0-implement — 配置 knip 跑反向核验时。

## 现象
knip 6 单项目 + 顶层 `paths` 配置下, 把 `packages/berth-scan-engine` (有自身 package.json `name=@berth/scan-engine` + 在 pnpm-workspace.yaml) 当独立 workspace 分析: root (main/renderer) 经 path-alias `@berth/scan-engine/*` 消费引擎源码的 import 不被解析 → 引擎核心文件 (engine/assets/runtime 等) 误报 unused + `@berth/scan-engine` 60 处 unlisted dependency。knip.json 顶层 `paths` 复刻 tsconfig alias 仍无效 (workspace 包名解析优先于 paths)。

## 根因
berth 的 root **不通过 workspace 包解析消费 scan-engine, 而是通过 tsconfig/vite path-alias 消费其源码** (node_modules 无 @berth 符号链接, root package.json 未声明该依赖)。knip 检测到 pnpm-workspace.yaml 后默认按 workspace 隔离分析, `paths` 对"已是 workspace 包名"的 import 不生效。

## 应沉淀的规则 (knip 在"alias 消费 workspace 源码"型 monorepo 的配法)
- `ignoreWorkspaces: ["packages/<pkg>"]` 排除该 workspace, 让 knip 单项目视角分析; 配合 root `paths` 复刻 tsconfig alias (`@berth/scan-engine` → src/index.ts, `@berth/scan-engine/*` → src/*), 引擎文件经 import 链可达, 不再误报 unused。
- `ignoreDependencies: ["@berth/scan-engine"]` 消除"内部 alias 被当外部 npm 依赖"的 unlisted 假阳性。
- **反向核验判据**: knip 报告里被 main/renderer 经 alias 实际消费的核心文件 (engine/scanner.ts, adapters/*/parsers) **不得**出现在 unused → 出现即 paths 没生效、配置失败。这是区分"真死代码报告" vs "零配置全量误报"的唯一可靠信号, 任何 knip 配置改动后必跑此核验。
- entry 必须列全多入口 (main / preload / renderer / scan-helper / asset-worker / cli-bin / index / adapter-api), 漏一个该子树全判死。
- 首次报告中等规模时用软门禁 `knip --no-exit-code` (仅 ubuntu 跑, 静态分析与 OS 无关) 起步; 清理死码 + allowlist 收敛到空再升硬门禁。
