# 工程摩擦记录

## 发生阶段

GH-100 (记忆页标签筛选组件重设计) `harness-0.0-new` / `harness-1.0-explore` 的小步提交。

## 现象

通过 **Bash 工具** 提交时, 误用了 PowerShell here-string 语法写多行提交信息:

```bash
git commit -m @'
chore(harness): ...
'@
```

bash 不认识 `@'...'@`: 它把开头的 `@` 当字面量、`'...'` 当单引号字符串、结尾 `@` 又当字面量, 结果提交信息首行变成孤立的 `@`, 末行多出 `@`, subject 被污染成 `@`。两个提交 (`5991eba` init、`9a3bf1c` explore) 都中招。

更糟的是: 共享工作区里其他 Agent (GH-101/GH-102) 已经在我的 init 提交之上提交, 把 `5991eba` 压成了历史中段。HEAD (`9a3bf1c`) 还能 `git commit --amend` 安全修复, 但 `5991eba` 一旦被压在别人提交下面, 在共享工作区重写它属于破坏性操作 (会改写他人提交), 禁止执行 → 该污染 message 永久留存。

## 工程师介入动作

- 对 HEAD 提交用正确的 bash heredoc 写信息到临时文件并 amend:
  ```bash
  cat > "$TEMP/msg.txt" <<'EOF'
  subject
  
  body
  EOF
  git commit --amend -F "$TEMP/msg.txt"
  ```
- 被压在中段的 `5991eba` 不重写, 留存并在本 friction 记录。

## 应沉淀的上下文或规则

- **Bash 工具里写提交信息只用 bash 语法**: 多行信息用 `<<'EOF' ... EOF`(单引号 heredoc 防 `$`/反引号展开)写入临时文件再 `git commit -F file`, 或单行 `-m "..."`。**严禁** 在 Bash 工具里用 PowerShell here-string `@'...'@` —— 那是 PowerShell 工具专用语法。
- 反之, 在 **PowerShell 工具** 里才用 `@'...'@`; 两个工具的多行字符串语法不可混用。
- **共享工作区的提交信息修复有时间窗**: 提交后若发现 message 写错, 必须**在其他 Agent 把新提交压上来之前**立刻 `--amend` 修 HEAD; 一旦被压成历史中段, 重写即破坏他人提交, 只能放弃修复。因此小步提交后应立即 `git log -1 --format=%B` 核对 message, 不要拖到下一步。

## 建议的流程改进
(由 harness-5.1-friction 消费)

在小步提交流程里加一步: 每次 `git commit` 后立即 `git log -1 --format=%B` 自检 subject/body 是否符合预期 (尤其多行信息), 发现污染当轮 amend; 工具选择上, Bash 工具固定用 heredoc/`-F`, PowerShell 工具固定用 here-string, 不跨工具套用。
