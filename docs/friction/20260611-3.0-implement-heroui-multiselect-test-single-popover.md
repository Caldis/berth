# 工程摩擦记录

## 发生阶段

GH-120 T4 (replay-kind-filter 组件测试), 3.0-implement。

## 现象

HeroUI `Select selectionMode="multiple"` 的组件测试在本地 Windows 全绿, 推送后 CI ubuntu/macos `pnpm test` 红 (`emits the new kind set on toggle…` 超时 1.2s 失败), windows job 绿 — 平台时序差异掩盖了测试自身的交互序错误。

根因: multiple 模式下点击 option **不关闭弹层**。测试若按"每次操作前都点 trigger 重新打开 listbox"的直觉写 (`openListbox() → click option → openListbox() → click option`), 第二次点 trigger 实际是**关闭**已打开的弹层, 随后 `findByRole('listbox')` 拿到的是卸载中的节点/等待超时; Windows 上 React Aria 的关闭时序碰巧让断言通过, Linux/macOS 必败。

## 工程师介入动作

无人工介入 — CI 红灯后 Agent 自查日志定位, 改为单弹层内连续点击两次 option (commit db0d3232), 本地+CI 复绿。

## 应沉淀的上下文或规则

- HeroUI (React Aria) `Select`/`Dropdown` multiple 模式: 选择动作不 dismiss 弹层。组件测试对同一弹层的多次选择/取消必须在**一次打开**内完成, 不重复点 trigger。
- 点击 trigger 是 toggle 语义: 弹层已开时再点 = 关闭。测试里出现第二次 `openXxx()` helper 调用即是信号。
- 本地单平台绿 ≠ 测试正确: React Aria overlay 的 unmount 时序平台相关, 凡涉及"重新打开弹层"的断言都要怀疑交互序而不是加 waitFor。

## 建议的流程改进

(由 harness-5.1-friction 消费) 组件测试涉及 HeroUI overlay (Select/Dropdown/Popover/Modal) 的多步交互时, 写测试前先确认该交互在产品语义下弹层是否保持打开; 优先在单次打开内完成多步断言。
