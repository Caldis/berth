# 工程摩擦记录

> task: GH-138 首页模块化仪表盘 (3.1-polish, 用户多轮判定完成度持续低于 Agent 自评)

## 发生阶段
3.1-polish (实现/打磨进行中, 用户中途打断纠正工作方式)

## 现象
Agent 把用户需求当**字面清单**逐条执行: 用户说"token 构成加饼图", Agent 就只在 token 构成
加饼图; 说"逐组件验收", 就机械跑清单。缺乏对**意图**的提炼与超额交付。用户原话:
"我感觉你只会做我说的东西, 但我希望你举一反三, 我说一你做 5, 这样才能给我惊喜。"
根因: Agent 把"最小满足需求 + surgical change"的默认守则, 错误地套用到了用户**明确要求高
主动性/高完成度**的创意打磨任务上 — 在该语境下"最小化"恰恰是失败模式。

## 工程师介入动作
1. 立刻切换工作模式: 在用户**明确要求**举一反三的任务里, 把每个显式需求当作"意图样本",
   推导其背后想要的完整体验, 主动补齐用户没说但顶尖专家会做的部分 (额外维度/形态/交互/
   动效/空态/趋势对比), 并主动沟通"超出你说的部分我做了什么", 而非逐条征求许可。
2. 落地前先取数据 ground truth (子代理探数据层能力), 保证"做 5"是真能落地的扩展而非空想。
3. 把扩展沉淀进 04-POLISH R2 计划 (磁盘), 让"做 5"的范围可追踪、可压缩续跑。

## 应沉淀的上下文或规则
- **"Simplicity First / surgical / 最小满足" 是默认, 不是铁律**。当用户显式要求"举一反三 / 给我
  惊喜 / 完全自定义 / 高完成度 / 全量一次到位"时, 用户的当下显式指令**覆盖**最小化默认 —
  此时正确做法是提炼意图、超额交付、主动扩展, 而不是缩到字面边界。
- **区分两类需求**: (a) 明确边界的事务/修复任务 → 守 surgical; (b) 开放式创意/打磨/产品塑造任务
  且用户要主动性 → 必须举一反三, 把"用户说的 1"当意图样本推导"该做的 5"。判错方向的代价 <
  缩在字面不敢扩的代价 (后者会被反复打回)。
- **举一反三 ≠ 堆功能**。是深挖意图后做**连贯的完整体验**: 围绕一个主题 (如"让仪表盘活起来:
  趋势对比/节律洞察/尺寸即信息设计") 系统扩展, 不是散点加无关 feature。
- **主动沟通扩展, 不逐条征许可**。用户要的是少操心 + 惊喜; 反复问"要不要做 X"本身违背"我说一
  你做 5"。决定 + 执行 + 事后说清"我额外做了什么、为什么"。

## 建议的流程改进
(由 harness-5.1-friction 消费)
- 不变量 12 (用户授权打磨/扩展) 补充触发词与模式: 出现"举一反三/给我惊喜/完全自定义/全量一次
  到位/尽可能丰富"等信号时, Agent 进入**超额交付模式** — 提炼意图、主题化扩展、主动沟通增量,
  暂时放宽 behavioral-guidelines 的"最小代码/不加未要求功能"约束 (该约束默认生效, 仅此类显式
  授权语境让位)。
- 与不变量 22 (前端质量逐组件验收) 协同: 超额交付的新组件同样走逐组件视觉验收。
