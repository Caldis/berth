## 发生阶段
3.0-implement (GH-115 T4/T5)。

## 现象
1. **gate 竞态**: T4 的 prepush 在后台跑时, 主循环并行开写 T5 源码 — prepush 的 vitest 收集的是工作区瞬时态, 不是被提交的 T4 状态; 失败原因被误读为环境 flake。
2. **部分重跑后提交**: T4 全量门禁报 `vitest=1` 时, 修了报错的两个文件后只重跑了那两个文件就提交 — 全量 run 里真正的失败因子 (Unhandled Error) 不附着在任何用例上, 部分重跑永远看不见它。
3. **vitest 语义盲区**: `Tests N passed (N)` + 退出码 1 = 存在 **Unhandled Errors** 段 (本例: React 19 错误边界测试中并发渲染恢复错误以 window error 事件逃逸)。"用例全过"不等于 run 通过。

## 工程师介入动作
无 (CI 拦截 + Agent 自查), 代价: 第二次红灯。

## 应沉淀的上下文或规则
- **prepush/全量 vitest 运行期间冻结工作区**: 不编辑任何 src/tests 文件; 要继续下一批, 只允许只读勘验或写 docs。
- **提交闸门 = 完整全量 run 的退出码**, 不是"我修过的文件绿了": 任何 gate 失败 → 修复 → **全量重跑** → 退出码 0 才能 commit。
- **vitest 退出码 1 且用例全绿 → 直接 grep 输出中的 `Unhandled Error`**, 不要按失败用例排查路径走。
- React 错误边界类测试在 React 19 + jsdom 下必须拦截 window error 事件 (`e.preventDefault()`), 否则恢复错误计入 Unhandled (模板已落 tests/renderer/page-error-boundary.test.tsx)。

## 建议的流程改进
- 把"全量重跑后才可 commit"与"gate 期间冻结工作区"并入 3.0-implement playbook 的提交清单。
