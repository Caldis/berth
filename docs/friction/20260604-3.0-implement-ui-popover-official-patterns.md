# 开源 UI 浮层行为修复前先查官方模式

## 发生阶段

GH-102 header 与 Hooks 检查浮层修复的 implement 阶段。

## 现象

第一版共享浮层实现已经解决 Portal 层级裁剪, 但 hover 细节仍有问题:

- popover 打开时会从左上角飞出。
- 鼠标从触发处移动到 popover 中间空隙时, popover 会隐藏。

用户指出不应继续凭经验猜, 应联网搜索最佳实践, 并把能力收敛到公共组件。

## 工程师介入动作

补查 Floating UI 官方文档后确认:

- `useHover` 的 `safePolygon()` 是处理 trigger 到 floating element 间 hover 转移的官方模式。
- 如果 floating element 的定位使用 `transform`, transform 动画应放在内层内容节点, 外层只负责定位, 否则会和定位 transform 冲突并产生从左上角飞出的视觉问题。
- `safePolygon` 文档说明移动到浮层过程中意外关闭时应增大 `buffer`; 本任务还需要 `requireIntent: false`, 让慢速穿过空隙时也保持显示。

随后将 `FloatingPopover` 改为 Floating UI Portal/fixed 定位、外层定位/内层动画、公共 `safePolygon` hover bridge, 并用 renderer 测试和 Electron 坐标实测验证。

## 应沉淀的上下文或规则

修复开源 UI primitive / 组件库的定位、hover、focus、dismiss、transition、Portal、collision 这类行为时, 不应只按经验改延迟或事件。先查官方文档、类型声明或源码中的推荐模式, 再把模式封装进共享组件。

如果问题表现为动画从错误坐标开始, 重点检查定位样式和动画样式是否写在同一个 DOM 节点上; 如果问题表现为 trigger 与浮层之间的空隙关闭, 重点检查组件库是否提供 hover intent / safe polygon / interactive tooltip 的官方能力。

## 建议的流程改进

在实现或验证阶段遇到第三方 UI primitive 行为问题时, 即使任务已经过了 design, 也要短暂停下补查官方文档或 primary source, 并把结论写回当前 work 的分析或方案产物。
