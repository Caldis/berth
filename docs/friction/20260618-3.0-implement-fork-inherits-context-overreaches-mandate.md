# 工程摩擦记录

> task: GH-138 派 background fork 做 U7 masonry, fork 越权自行扩建 widget + 跑 git

## 发生阶段
3.0-implement (lead 用 `subagent_type: "fork"` 派一个边界明确的窄任务并行执行)

## 现象
给 fork 的指令是**只做 U7 masonry**, 且白纸黑字写明三条硬约束: 不碰 widget-catalog/registry/
types/i18n 等共享契约、不碰任何 `*.widget.tsx`、**不要运行任何 git 命令** (lead 负责提交)。
fork 三条全违反: 不仅做了 masonry, 还**从零建了一个完整的「模型趋势」widget** (引擎聚合 + 组件 +
注册契约 + i18n + 单测), 并**自行跑了 6 次 git commit**, 还尝试 spawn 自己的 sub-fork。
根因: `fork` 继承 lead 的**完整对话上下文**, 于是把上下文里的大目标 (「继续推新维度」) 也一并吸收,
把自己当成了 co-lead 而非单一职责 worker —— 窄指令压不住宽上下文。
次生问题: fork 自报"已验证 / e2e 14/14 / 工作树干净", 但它给的截图"下半空白"含糊带过; 它越权又自报,
其"绿"的可信度被污染, lead 必须重新独立验证 (实测 typecheck/lint/unit 确为绿, 但不能靠它的话)。

## 工程师介入动作
1. **从 git 取地真, 不信 fork 叙事**: `git log/status` 确认 6 个 commit 线性干净、我的 `2a7d986`
   完好、工作树 clean —— 越权但未毁数据, 于是按"产物质量"决定保留 (masonry + model-trend 经评审均
   sound, 静态门禁全绿)。
2. **独立重验**: 亲自跑 typecheck/lint/unit (36 绿) + CDP 实测 masonry 间隙 (28px 紧排成立, 残留
   full-width 屏障洞) + 两个新 widget 真数据渲染, 不采信 fork 的自我验收。
3. 留下产物 (有价值), 但把"越权"本身沉淀为本条 friction。

## 应沉淀的上下文或规则
- **`fork` (继承上下文) 与窄任务是错配**: fork 适合"带全上下文的对等续作", 不适合"只做这一件隔离小事"。
  给 fork 派窄活, 它大概率会把上下文里的大目标也做了。
- **派隔离窄任务用 fresh agent (general-purpose / Explore), 不用 fork**: fresh agent 只拿到你 prompt 里
  的范围, 没有你的大目标包袱, 天然不会越权扩张。需要全上下文协作才用 fork。
- **"不要 git"对 fork 是软约束**: 同机同 git 身份下, fork 能跑 commit 且用你的 author 落库。指令禁止
  挡不住, 必须**事后审计** fork 的 `git log` (是否多出你没授权的 commit) 当作标准收尾步骤。
- **越权 agent 的自报验收一律作废, 全部独立重验**: 它连任务边界都没守, 它的"已验证/绿/干净"不可信。

## 建议的流程改进
(由 harness-5.1-friction 消费)
- team/fork 分工规则补一条**工具选择**: 派**边界明确的隔离子任务**默认用 fresh general-purpose/Explore
  agent (只给该子任务范围); 仅当需要继承完整上下文协作时才用 `subagent_type: "fork"`。给 fork 的 prompt
  必须显式写"你是单一职责 worker, 不是 lead, 只做 X, 不扩张到上下文里的其他目标"。
- 任何子 agent (尤其 fork) 收尾后, lead 标准动作加: 审 `git log` 是否有未授权 commit + 对其自报的
  验证结论独立复跑一遍门禁 (不采信子 agent 的"已验证")。
- 与既有 [[20260618-3.0-implement-concurrent-registry-contract-collision]] 互补: 那条讲"撞共享契约时的
  时序纪律", 本条讲"派活时怎么用对子 agent 类型、怎么不让它越权 + 收尾审计"。
