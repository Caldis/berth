## 现象
- 全局 scope 下 [约定] 等页项目级资产**闪现后消失、周期性出现又消失**。用户打开 app 不到 10s 发现; Agent 在此前 cap-2/3/4 + 完成度 UX 多个切片中全程未发现。
- Agent 的验证全部停留在静态层: 各组件单独 unit test 绿、typecheck、lint、CI 绿。**从未真正运行 app 观察运行时动态行为**。
- bug 是**涌现/时序型**: 每个组件单独都正确 —— scanner partial 设计为 deep-only (快首屏, 注释明写)、`applyAssetProgress` 整体覆盖 (累积扫描语义)、scope 过滤正确。错误只在**组合 + 时序**涌现: deep-only partial (无其它项目 shallow) 覆盖了含 shallow 的完整 snapshot, 且 agent 写 session → watcher → 频繁 refresh → 反复覆盖。
- 结构上单测测不到: 各组件测试 mock 掉时序与彼此, 组合涌现不在任一测试视野; CI 不跑 e2e; 连 cap-4 的真实 chokidar e2e 也只断言 `snapshot.id 稳定` (证"走增量"), **没断言"用户持续看到项目级"** —— 测错了维度。

## 工程师介入动作 (这次的正确做法, 作为可复用 recipe)

- `dev:agent start --debug-port 9333` 真跑独立实例 + CDP `connectOverCDP` 采集 renderer console 时序 → 决定性复现: `PROGRESS shallow=0 ↔ SETSNAP shallow=86` 交替 = 闪烁。main log 在 `<instanceDir>/electron-vite.log`。
- 修复后 CDP 重跑验证: `PROGRESS partialShallow=0, kept=86, mergedShallow=86` (保留, 不再闪)。
- 加回归单测断言"shallow 资产在 deep-only partial tick 后存活"。

## 应沉淀的上下文或规则
- **错误类型命名**: observable runtime behavior bug (可观测运行时行为 bug) / temporal-emergent bug (时序涌现)。区别于 logical bug (单组件逻辑/类型/边界)。AI 擅长 logical (代码与测试里可见), **结构性弱于 observable** —— 它只在真跑 + 观察动态时显现, 而 AI 没有"看屏幕"的感知通道, 默认用符号推理 (代码/断言) 代替观察。
- **根本盲区**: 把"测试绿 + 类型对 + CI 绿"等同于"功能正确"。这只覆盖 **code-level correctness**, 不覆盖 **observable correctness** (用户实际看到什么 + 随时间如何变化)。两者之间有鸿沟, 时序/渐进/多源类功能尤甚。
- **强制规则**: 凡涉及"数据如何到达 UI + 随时间如何变化"的功能 (渐进扫描/流式 partial/SWR/多数据源/缓存/增量), verify **必须真跑 app 观察动态行为**, 不能只 unit/CI/单帧截图。具体: 盯屏看过渡、刷新、多事件交织时的表现; 自问"如果用户盯着屏幕 30 秒会看到什么"。
- **测试维度**: 这类功能的集成/e2e 断言要测 **observable** ("用户持续可见什么"), 不只 internal ("组件契约 / id 稳定")。cap-4 e2e 断言 id 稳定却漏了"项目级可见" = 测错维度的反面教材。
- **主动怀疑清单**: 多个数据源写同一 UI 状态时, 追问 —— 几个源? 各自内容一致吗 (deep vs deep+shallow)? 谁可能覆盖谁? 中间态完整吗? last-writer-wins 会丢信息吗? partial/stream/SWR/cache 天然有"不完整中间态覆盖完整态"的风险。
