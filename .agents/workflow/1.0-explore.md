# harness-1.0-explore — 探索 (Explore 阶段)

目标: 把外部需求与内部现实对齐, 建立对现状的真实理解。

前置: INDEX.phase == explore。

步骤:
1. 读取 00-PRD.md / 00-BUG.md 原始输入。
2. 用 `.agents/tools.md` 列出的工具拉取关联上下文 (代码、关联模块、历史设计)。
   - 用户反馈“页面/面板/视图为空或显示不对”时, 默认先按 berth 产品自身定位: renderer 页面 -> hook / IPC -> main 数据层。确认产品链路无问题后, 再外扩到 Claude Code / Codex / harness / 宿主环境的同名概念。
   - 任务涉及外部产品、平台、CLI、字段契约、费用口径或运行时行为时, 先用英文检索官方文档或 primary source; 官方无公开契约时, 才用本机样本作为 fallback 并标注。
   - 常规联网研究只用 WebSearch/WebFetch。抓取被 403 / Cloudflare 拦截时, 依次尝试官方 `.md` 页面、官方镜像或公告页、搜索摘要; 仍拿不到就跳过并标注限制, 不打开 GUI 浏览器绕过。
   - 当 source 是 `docs/issues/` 且其中含具体"根因候选 / X 平台产品 bug"判断时, 这些是**待验证假设, 不是 ground truth**: explore 第一步先实机复现 / 拉 CI 实际断言值 / 写最小探针, 证伪或证实该判断, 再决定改产品代码还是测试; issue 写得越具体越要警惕被当结论 (friction 20260617-issue-hypothesis-needs-ground-truth, 同构 GH-117 / GH-137)。
3. 阅读 `docs/ARCHITECTURE.md` 项目地图与相关模块文档。
4. 产出 `01-ANALYSIS.md`:
   - 现状理解 (涉及哪些进程/模块/IPC 契约)
   - 关联与依赖 (谁调用谁, region/scope 差异)
   - blast radius 用符号边界判定 (import 关系 / JSX 使用点 / 类型引用), 不用 grep 子串计数 — 子串会把注释、同名变量、文案算进来虚高影响面 (friction 20260606-heroui-migration)
   - 全局搜索入口 vs 页面内部搜索 vs 顶部导航搜索是三类不同契约, 改动任何一类前先确认边界与快捷键 (Ctrl/⌘K) 路由优先级, 不凭单页观感删全局入口 (friction 20260603-sidebar-search-scope)
   - 任务分类与 debt 校准: 核对 `type`、`maintenance.subtype`、`source.kind`、scope、risk、areas 是否仍准确; 若与 new 初始估算不同, 更新 INDEX.md `debt.estimate` 并追加 `debt.revisions[]`
   - 验收标准 (逐条编号, 后续 SPEC 与 verify 据此核对)
   - 未决问题 (留给 design 向人澄清)
   - UI/list 类 bug 必须做用户可见字段审计: 标题、日期、路径/项目、token、cost、模型、duration、空态、加载态、错误态; 同一扫描共享数据契约的页面, 不只扫用户点名页面。
   - 前端或 UI 相关任务必须增加“界面质量与交互验收”小节: 记录现有页面结构、设计系统用法、信息密度、主要用户路径、可见状态、交互反馈、响应式和可访问性风险。
5. 更新 INDEX.phase = design。

不编码。摩擦记入 docs/friction。若探索中发现已验证但不属于当前主线验收范围的产品问题, 记入 docs/issues 并在 01-ANALYSIS.md 交叉引用。完成提示用户: `harness-2.0-design`。
