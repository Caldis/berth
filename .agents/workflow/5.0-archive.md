# harness-5.0-archive — 归档

目标: 完成一个任务。

前置: verify 全部通过。

步骤:
1. GitHub Project: 运行 `node scripts/harness-projects.mjs done docs/works/{task}`。
   - 该命令会使用 INDEX.md 里的 `gh_project.item_id`, 将 Status 置 Done, 再回读 Project item 确认。
   - 若缺少 `project` / `read:project` scope, 提示用户运行 `gh auth refresh -h github.com -s project,read:project` 后停止; 不移动目录。
   - 若缺少 `gh_project.item_id` 或远端回读不是 Done, 停止 archive。
2. 将 INDEX.phase 置 archive。
3. 将 `docs/works/{task}/` 整体移动到 `docs/works/_archive/{task}/`, 避免污染上下文。
4. 提交并推送代码 (遵守提交规范), 准备提测。提交前只暂存自己相关文件, 用 `git diff --cached` 核对 staged 集合, 不提交无关工作区改动。共享工作区禁止 `git add -A`、`git add .` 和目录级 add; 归档移动目录时用 `git mv` 或显式列出本轮任务的新旧路径, 不把同目录下他人的 untracked 任务带入提交。推送前先运行本地归档检查, 再运行 `pnpm harness:ci:baseline` 查看当前分支最近 GitHub Actions 状态; 若远端已经被当前会话提交推红, 且当前提交不是修 CI, 停止 archive, 回 implement 修红灯。
5. 推送后运行 `pnpm harness:ci:wait`, 等待新 SHA 对应 GitHub Actions run。若 CI 失败, 保留任务上下文, 回 implement 修复, 不把任务归档为完成。
6. 若任务关联 `docs/issues/`, 更新其状态并交叉引用归档路径。GitHub Issue 不默认关闭; 只有 PR closing keyword 或用户明确要求时才关闭。
7. 汇总本次产生或关联的 friction / issues:
   - friction: 列出当前任务中新建或修改的 `docs/friction/` 文件, 说明是否建议运行 `harness-5.1-friction`。
   - issues: 列出当前任务中新建、修改或交叉引用的 `docs/issues/` 文件, 并可运行 `pnpm harness:issues` 查看当前堆积。
   - 只提醒用户可选下一步, 不自动进入 `harness-5.1-friction` 或 `harness-5.2-issues`。

产出: 任务归档 + commit + gh project item 关闭。
