# harness-3.0-implement — 实现 (Implementation 阶段)

目标: 按 03-PLAN.md 实现。

前置: INDEX.phase == implement 且存在 02-SPEC.md 与 03-PLAN.md。

步骤:
1. 按 03-PLAN.md 任务顺序逐项实现。
   - 默认流程是 harness workflow; Superpowers 只能作为方法参考, 不执行 `executing-plans` 的用户选择流程, 不创建 active `docs/superpowers/plans` 或 `docs/superpowers/specs`。
   - Agent 自主判断并行或顺序执行: 文件不重叠、模块边界清楚、测试可独立运行时可并行; 同一批文件反复修改、测试强耦合、任务依赖前一步结果、或涉及全局迁移/状态机/脚本入口时顺序执行。不得把 subagent 并行或主 session 执行作为用户选择题。
2. 每项先处理测试, 再写实现:
   - 先定位或新增目标测试文件; feature / bug / maintenance / 行为变更优先写一个会失败的测试。
   - 后写最小实现, 跑目标测试通过。
   - 如果本项确实不适合自动化测试, 在 03-PLAN 对应项写 `tests: not needed - <reason>` 和替代验证命令/人工验收证据。
   - 每个实现项必须有测试证据或明确例外理由, 否则不得勾选完成。
   - 通过后必须立即小步提交; 每次只暂存自己相关文件, 用 `git diff --cached` 核对 staged 集合。不得把多个已完成项堆到最后一次性提交; 若本轮只改 `INDEX.md` phase、`03-PLAN.md` 复选框或测试证据等进度状态文档, 先等下一次代码、测试、设计产物、归档或其他阶段结果一起提交并推送。若不能提交, 必须在当轮说明阻塞原因。
   - **门禁新鲜度**: 门禁必须跑在「即将提交的那个工作树状态」上 — staged 集合在上次门禁后有任何新改动, 必须重跑; 部分重跑通过不能替代全量重跑后再提交; `git push` 与门禁命令链分离执行, 不串在同一命令里; prepush 后台运行期间冻结工作区, 不并行编辑 (见 friction 20260607-stale-green / 20260610-gate-race)。
   - **撤销纪律**: 对未提交文件做实验性注入 (探针 log、临时改动) 后, 撤销只能用反向 Edit 删除注入行; 禁止 `git checkout/restore <file>` — 会把整文件回滚到 HEAD 丢掉未提交工作 (friction 20260610-git-checkout-wipes)。
   - 实现期跨切面约束 (按改动类型触发):
     - 改 `runtime.search` / 作用域过滤 / 搜索相关: 提交前必须本地跑 `project-scope.e2e.ts` 等相关 e2e, 不靠 CI 兜底 (friction 20260606-scope-filter)。
     - 同一状态经 invoke 回复 + `webContents.send` 双通道下发: 终态必须在 push 通道补发一次保序, 单测断言最后一条 push 事件为终态 (friction 20260607-ipc-ordering-race)。
     - 给共享组件新增 react-router hook: 同步 grep 该组件所有测试 render 点, 补 MemoryRouter 包裹 (friction 20260607-router-hook)。
     - 跨文件路径解析测试: 禁硬编码 `D:\\` 反斜杠字面量, 用 `path.join/resolve` 构建 — ambient path 模块平台相关 (friction 20260607-backslash-posix-ci)。
     - 改 IPC 契约表 (IpcEvents/IpcChannels) 前: 先 grep `webContents.send` 实发调用点核对 payload 真实形状; 契约对账方向是 表←实现, 把表当真源会固化历史漂移 (friction 20260610-contract-table-trust)。
     - 用 e2e 验证源码改动前: 先 `pnpm build` 或确认 dev `--watch` 已 rebuild — e2e 跑的是 out/ 产物不是源码; 平台/CI 红的第一步是 stash 本次改动跑 baseline 对比 (friction 20260608-e2e-stale-artifact)。
3. 将 03-PLAN.md 当作活清单: 完成项勾掉, 与方案的偏差就地记录在 PLAN 中。
   - 如果实现中发现 debt 初估不准, 立即更新 INDEX.md `debt.estimate`, 并在 `debt.revisions[]` 记录阶段、日期、from/to 和 reason。
   - 实现项完成后若 Project 字段需要反映最新 estimate, 运行 `node scripts/harness-projects.mjs ensure docs/works/{task}` 同步。
4. 遇到工程摩擦 (卡顿、被迫手动补的上下文、被迫的手动修正) 不就地消化, 写入
   `docs/friction/{YYYYMMDD}-3.0-implement-{summary}.md` (模板见 docs/friction/_template.md)。
5. 遇到已验证但不属于当前主线验收范围的产品 bug、功能缺口或改进项, 写入
   `docs/issues/{YYYY-MM-DD}-{BUG|FEATURE|IMPROVEMENT}-{summary}.md`, 并在当前 PLAN 中交叉引用; 不顺手修, 除非用户明确扩大任务范围。
6. 全部任务完成后, 更新 INDEX.phase = verify。

产出: 代码 + 单测 + 更新后的 03-PLAN.md。完成提示用户: `harness-4.0-verify`。
