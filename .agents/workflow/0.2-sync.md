# harness-0.2-sync — 多设备同步续跑

输入: 任务标识 (目录名 / `GH-123` / `#123` / issue URL, 同 0.1-continue) 或为空。

适用: 在另一台设备 (或另一个 Agent) 推进过同一任务后切回本机续跑。多设备 / 多 Agent 协作下本地工作树往往落后远端; 本步骤先把工作树与远端对齐并完成增量交接, 再按 `harness-0.1-continue` 续跑。它是 0.1-continue 的"同步前置", 不替代续跑本身。

步骤:

1. 同步前置 (保护未保存工作):
   - `git status --short`: 工作树若有本人未提交改动, 先按 COMMIT_POLICY 小步提交, 或 `git stash`; **严禁用 sync 覆盖未保存工作**。
   - `git rev-parse HEAD` 记录当前 HEAD 作为交接基线 (步骤 3 用它算增量)。
   - `git fetch origin`。

2. 对齐本地与远端 (按分叉情况, 只在主分支工作):
   - **落后** (远端领先, 本地无独有提交): `git merge --ff-only origin/<branch>` fast-forward。
   - **领先** (本地有未推送提交, 远端无新): 上个设备可能漏 push; 与用户确认后本地即最新, 直接进步骤 3。
   - **分叉** (双方都有独有提交): **停止**, 向用户报告分叉并列出双方独有提交, 询问策略 (默认 `git rebase origin/<branch>`, 冲突人工解决); 不得擅自 `force-push` / `reset --hard` / 丢提交的 rebase — 不可逆操作必须先获用户确认。

3. 增量交接 (必做 — 理解另一设备改了什么):
   - `git log --oneline <基线HEAD>..HEAD` 逐条归纳拉进来的提交: 落地了什么、是否触及你要跟进的文件/方向、是否与你计划的下一步重叠或冲突。
   - **吸收新沉淀**: 读本次拉进来的 `docs/friction/`、`docs/issues/`、`docs/works/{task}/` 变更 — 另一设备可能留下新规则 / 教训 / issue (如新增 verify 硬门禁), 必须纳入后续工作, 不得续用过时计划。

4. 续跑: 读 `docs/works/{task}/INDEX.md` 的「续跑指南」与 frontmatter, 转 `harness-0.1-continue` 按 `phase` 路由到当前阶段继续。

5. 对齐校验 (动手前): 跑一次本机门禁 (typecheck / lint / test) 确认合并后的工作树在本机绿 — **远端绿不等于本机绿** (原生模块 ABI / 平台差异 / 构建产物陈旧)。

不变量:
- 不可逆 git 操作 (`force-push` / `reset --hard` / 丢提交的 rebase) 须先获用户确认。
- 续跑前必须完成步骤 3 的增量交接 + 吸收新沉淀; 跳过会用过时认知覆盖他人新工作。
- 本步骤只做同步 + 路由, 不直接落实现; 实现仍走 0.1-continue 路由到的阶段, 受其门禁与提交策略约束。

产出: 工作树与远端对齐 + 增量交接摘要 + 本机门禁绿 + 续跑当前阶段。
