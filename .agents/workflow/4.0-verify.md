# harness-4.0-verify — 验证 (Verify 阶段)

目标: 完成完整测试 + code review + 前端视觉/交互验收。人在此确认验收。

前置: INDEX.phase == verify。

步骤:
1. 测试覆盖审计:
   - 对照 03-PLAN, 确认每个实现项都有测试证据或明确例外理由。
   - 对照本任务 diff, 确认每个行为变更都有 unit / renderer / e2e / harness 测试之一覆盖; 不适合自动化测试的项必须有替代验证证据。
   - 若缺测试证据或例外理由含糊, 回写为 03-PLAN 新任务, 将 INDEX.phase 退回 implement。
   - 校准 INDEX.md `debt.final`: 依据最终 diff、测试范围和剩余风险填写 incurred/repaid/net/scope/risk/areas/confidence/rationale。若 final 与 estimate 差异明显, 追加 `debt.revisions[]`。
2. 机械检查: `pnpm lint`, `pnpm typecheck`, `pnpm test` 全绿 (CI 亦会拦截)。
   - 本地检查通过后, 查看当前分支最近 GitHub Actions 状态: `gh run list --branch <branch> --limit 5`。
   - CI 成败以 `gh run view <id> --json status,conclusion,headSha` 的 `conclusion` 字段为准 (`success`/`failure`), 不只看退出码。**禁止把判定命令接 `| tail`/`| head`/`| grep` 后再读 `$?`** —— `$?` 反映管道末端命令 (如 `tail` 恒 0), 会把失败 CI 误读为成功; 需上游退出码时用 `${PIPESTATUS[0]}` / `set -o pipefail` / 单独运行。优先用封装好的 `pnpm harness:ci:wait --sha <full-sha>` / `harness:ci:baseline` (内部按 conclusion 判定)。
   - 若最新 CI failure 来自当前会话提交, 且本任务不是专门修 CI, verify 失败: 先回 implement 修红灯, 不继续新功能、polish 或 archive。
   - 若本任务就是 CI 修复, 允许在远端红灯基线下继续, 但提交推送后必须等待新 SHA 的 GitHub Actions run 完成。
3. Code Review (只看机器判断不了的部分):
   - 对照 01-ANALYSIS.md 验收标准逐条核对产出。
   - 对照 02-SPEC.md 与 docs/ARCHITECTURE.md, 检查是否偏离设计、越界、违反 MVVM/进程隔离。
   - 运行 `pnpm harness:stats` 查看 debt pool 状态; 若 `status=requires-override`, 非 maintenance 任务必须在 INDEX.md 写明 `debt.override_reason`。
   - 运行 `node scripts/harness-projects.mjs check --strict` 检查 Project 状态与可读字段值; 字段缺失时先运行 `node scripts/harness-projects.mjs fields ensure`。
   - 非本地门禁可由子代理执行: Project strict check 可交给子代理处理; 主 Agent 必须消费成功结果后才可判定 Project 门禁通过。
4. 前端验收: 启动应用, 截图, 走通受影响界面的交互流程, 完成视觉与交互验收 (Agent 需"看到界面、摸到设备")。
   - 前端或 UI 相关任务必须对照 02-SPEC/03-PLAN 的“界面质量与交互验收”逐条检查, 包括布局层级、信息密度、组件一致性、交互反馈、加载/空/错误/禁用/focus 状态、响应式、可访问性、文案/i18n。发现缺口时回写 03-PLAN, 不把后续 polish 当作必需问题的替代。
   - 主观视觉 / 布局 taste 改动 (贴顶、遮罩范围、间距、按钮位置、对齐) 的最终裁判是用户, 不是 Agent: 先产出截图并显式请用户确认“是不是你要的样子”, 再跑机械门禁; 不把“测试绿 + 坐标对 + 界面质量条目打勾”当作视觉验收通过 — 坐标和测试只证明实现符合 Agent 自定的方案, 证明不了那是用户要的。**例外**: 用户已明确要求 Agent 自主完成该需求 (autonomous / 不打断 / 一次做完) 时, 跳过用户视觉确认, 由 Agent 按界面质量条目自验并自担该判断, 不停下等确认、不打断自主循环。
   - **数据流 / 时序 / 渐进类功能必须验收"随时间变化的行为", 不能只看单帧或只判静态绿**: 流式 partial、SWR、多数据源写同一状态、缓存、增量索引、后台扫描等, 真跑 app 观察多次刷新 / 多事件交织 / 扫描进行中 vs 完成下的实际表现, 用 `--debug-port` CDP 采集**时序 log 或状态序列** (跨组件 boundary 各打一条计数 log), 不是一张截图。断言落在 **observable** (用户随时间持续看到什么), 不是 internal (snapshot id 稳定、组件契约)。单组件 unit 全绿 + CI 绿**证明不了**多组件组合 + 时序下的可观测正确性 — 这类 bug (中间态覆盖完整态、last-writer-wins 丢信息、竞争闪烁) 只在真跑观察动态时显现。多源写同一 UI 状态时主动追问: 几个源? 内容一致吗? 谁覆盖谁? 中间态完整吗? (见 `docs/friction/20260609-4.0-verify-static-green-over-runtime-observation.md`)
   - **先观测用户 dev, 但不接管、不复用、不清理**。如果用户已经运行 `pnpm dev` / `npm run dev`, 记录其 electron-vite PID 与 Electron 主进程 PID, 作为验收前后保护对象。
   - Agent 需要真实应用实例时, 使用独立 lifecycle: `pnpm dev:agent start --id <stable-id>`。需要 renderer 路由切换、展开态、选中态或截图辅助时, 优先加 `--debug-port <port>` 获取稳定 DevTools/CDP 入口。该命令会传 `--berth-agent-instance=<stable-id>` 与独立 `--user-data-dir`, 并把 owner pid/state/log/debug port 写入系统临时目录。
   - CDP 只用于只读检查与交互, **不要用它改写 `window.api.*` 构造数据态**: contextIsolation 下 contextBridge 绑定在页面上下文不可重赋值且静默失败 (jsdom 测试可行, 真机不行)。构造"主进程数据为空/特定形态"的真机场景, 用第二个 agent 实例 + 环境覆写 (如 `HOME=$(mktemp -d) pnpm dev:agent start --id <id>-empty`); 另外 locale/JSON 热更新可能整页 reload 清掉 CDP 注入态, 注入类操作避开 pending HMR (见 friction 20260610-4.0-verify-cdp-cannot-stub-contextbridge)。
   - 验收结束只能执行 `pnpm dev:agent stop <stable-id>` 清理本轮 Agent 实例。禁止使用按仓库路径批量清零的 `pkill` / `taskkill` / `Stop-Process` 命令, 因为它们会误杀用户 dev。
   - 需冷启动验证 `main` / `preload` / `BrowserWindow` / titlebar 等改动时, 冷启动的是 agent-owned 实例, 不是用户 dev。用户 dev 的刷新由其自己的 `electron-vite dev --watch` / HMR 处理。
   - 截图前轮询确认目标 Electron 主进程存活, 且 command line 带本轮 `--berth-agent-instance=<stable-id>` 或 state 中记录的 pid; 不要只看 vite 端口。按窗口 id 截图。截图存系统临时目录 (`$env:TEMP` / `os.tmpdir()`), 禁止入项目目录, Windows 不用 `/tmp`。
   - 进程检测必须区分主进程和 helper 子进程: Electron 主进程通常是 `electron .` 或加载 `out/main/index.js`, helper 子进程带 `--type=`。
   - UI 改动 (布局/间距/样式) 的视觉验收必须用 `/frontend-design:frontend-design` 指导设计判断, 不靠拍脑袋调数值; 间距/对齐需有明确依据 (与既有元素对齐、符合平台 HIG)。
   - Electron `main` / `preload` / `BrowserWindow` / frameless titlebar / `-webkit-app-region` 改动必须冷启动真实应用实例验证, 不能依赖 renderer HMR 或只验证隔离测试实例。
   - 自绘窗口 chrome、标题栏按钮、拖拽区、系统窗口按钮等原生命中相关改动, 最小验收为: hover 有视觉反馈、真实 OS 鼠标点击生效、主进程窗口状态可观测变化 (如 maximize/restore 后读取 `BrowserWindow.isMaximized()` 或 Win32 `IsZoomed`)。
   - 这类命中验证禁止只用 Playwright/CDP 的 `locator.click()` 作为最终证据; CDP 点击可能绕过系统非客户区与 draggable region 命中。Windows 需要用 Win32 `SetCursorPos` + `mouse_event` 或同等级真实输入; macOS 需要用系统级鼠标事件工具。
   - Windows 进程检查需区分主进程和 helper 进程: 用 `Get-CimInstance Win32_Process` 查看 `electron.exe` 命令行, 主进程通常是 `electron.exe .` 或加载 `out/main/index.js`, helper 进程带 `--type=`。验证前后都要确认目标窗口对应的是本轮 agent-owned pid / `--berth-agent-instance=<stable-id>`。
   - Windows 脚本不要把 `$pid` 当局部变量名; PowerShell 变量名不区分大小写, `$PID` 是只读自动变量。保存窗口进程 id 时用 `$windowPid`、`$windowProcessId` 或 `$targetProcessId`。
   - Windows UI 截图需用真实 `electron.exe` 主进程窗口, Playwright/CDP 只负责交互。不要用 `_electron.launch()` 返回进程的 `MainWindowHandle` 当截图句柄; 该 PID 可能没有主窗口句柄。高 DPI/显示缩放下, 优先用 Win32 枚举目标进程可见窗口, 再用 DWM `DWMWA_EXTENDED_FRAME_BOUNDS` 获取物理像素窗口边界后 `CopyFromScreen` 裁剪。`CopyFromScreen` 前必须确认目标窗口置前且无遮挡; 否则只能作为辅助证据。
   - Windows 高 DPI/显示缩放下, 截图和点击坐标不要混用: `CopyFromScreen` 裁剪使用 DWM physical bounds; `SetCursorPos` / `mouse_event` 点击使用 `GetWindowRect` 返回的逻辑坐标。若直接用 DWM bounds 计算点击点, 150% 缩放环境会偏移并点不中。
   - 真实鼠标点击前必须重新获取当前 agent-owned Electron 主进程、窗口 handle 和窗口矩形; dev server / Electron 重启后, 禁止复用旧 PID、旧 handle、旧窗口矩形或 CDP `page.setViewportSize()` 后的 viewport 坐标。优先复用既有 e2e helper, 不临时手写坐标脚本。
   - 对 renderer 状态、按钮选中态、路由切换、表格内容这类页面行为, 可用 Playwright 控制 agent-owned Electron renderer 直接断言并保存 renderer 截图; 若 Playwright 管理浏览器未安装且只需 renderer 辅助截图, 可显式指定本机 Chrome / Edge `executablePath`, 不为普通 verify 临时下载浏览器; 若截图要作为真实桌面视觉证据, 仍按上一条用真实窗口句柄裁剪。
   - `dev:agent guard after` 若报告用户 dev 的 Electron 子进程重启但同一 dev server 父进程仍在且已有新的无 `--type=` Electron 主进程, 视为正常 restart 记录; dev server 父进程消失才视为高风险。
   - **瞬态 UI 验收必须冷重启**: 扫描/加载进行中的瞬态界面截图, 必须冷重启 agent-owned 实例后立即连接轮询采集; `page.reload()` 无效 — 主进程 runtime 是热单例快照缓存, reload 后直接出终态 (friction 20260607-scanning-state-cold-restart)。
   - **virtuoso sticky 头**: react-virtuoso 行绝对定位会穿透容器 padding; sticky 分组头的间距只能做进头自身的不透明 padding, 不能靠容器 padding / scrollPaddingTop; 验收用 CDP `elementFromPoint` 实测穿透 (friction 20260606-virtuoso-sticky)。
   - **HeroUI 控件迁移**: 门禁必须全量 `pnpm test` (跨文件测试受迁移影响, 单文件绿不可信); 浮层 (popover/modal/tooltip) 改动必须本地补跑 e2e — prepush 不含 e2e (friction 20260606-heroui-migration / 20260605-heroui-v2-setup)。
   - **vitest 全量失败集漂移**: 失败集随运行变化时, 先查外部负载 (并发 agent/构建), 再默认隔离重跑确认; 禁用 singleFork 串行 renderer 测试 — 跨文件污染 module-level 缓存产生假失败 (friction 20260610-vitest-flaky-singlefork)。vitest 显示全绿但退出码 1 = 有 Unhandled Errors, grep 输出中 `Unhandled` 定位。
   - **dev:agent stop EPERM (Windows)**: 首次 EPERM ≠ 没停 — 进程通常已 kill, 失败只在删 profile 临时目录; 用 `Get-CimInstance` 确认进程已退出后, 重试或忽略 temp 残留; 仍禁止 taskkill 批量清 (friction 20260609-stop-eperm)。
   - **macOS 截图**: `dev:agent screenshot` 仅 Windows 实现; macOS 优先 CDP `page.screenshot()` + 运行时坐标检查 (elementFromPoint 反推), 不靠系统窗口裁剪与猜坐标 (friction 20260603-macos-screenshot)。
   - **CI 红灯归因**: 共享分支 CI 红时, 用 `git show --stat <sha>` + `git log -- <failing-file>` 判定归属; 红点属他人在途提交时不背锅也不越界修, 在汇报中自证即可 (friction 20260604-ci-red-foreign-commit)。
   - verify 过程中若遇到已验证的工具链 workaround、截图/进程/环境类问题、或用户纠正, 不等最终复盘: 先写入 `docs/friction/{YYYYMMDD}-4.0-verify-{summary}.md`, 必要时同步更新 workflow 规则, 跑 `pnpm harness:check` 通过后再继续最终汇报。
   - verify 过程中若发现已验证但不属于当前主线验收范围的产品 bug、功能缺口或改进项, 写入 `docs/issues/{YYYY-MM-DD}-{BUG|FEATURE|IMPROVEMENT}-{summary}.md`, 并在当前 verify 记录或 PLAN 中交叉引用; 不把旁支问题改成当前任务修复项, 除非用户明确扩大任务范围。
5. 不通过项: 回写为 03-PLAN.md 新任务, 将 INDEX.phase 退回 implement, 重新进入开发循环。
6. 全部通过后:
   - 若用户主动要求 Polish, 或 Agent 判断当前任务复杂且值得进一步检查, 只能先询问用户是否进入 `harness-3.1-polish`; 用户明确同意后再进入。
   - 若用户未要求或不同意 Polish, 提示用户确认验收, 然后 `harness-5.0-archive`。
   - 如果用户已明确认为任务完成或要求提交, 不要停在未提交工作区: 立即进入 archive 的归档、提交、推送与 CI 检查流程。若等待用户确认而暂不 archive, 最终说明必须明确“尚未提交, 下一步 archive/commit”。
   - 非本地门禁可由子代理执行: 推送后的 `pnpm harness:ci:wait --sha <full-sha>` 可交给子代理等待; 主 Agent 必须消费成功结果后才能声明 verify/提交链路完成。CI failure 由主 Agent 回 implement 修复。

评审记录留在 PR/CI, 不进入项目持久层。
