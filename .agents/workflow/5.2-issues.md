# harness-5.2-issues — 问题收敛

目标: 消费 `docs/issues/` 下长期堆积的产品问题、功能请求与改进项。

触发:
- 用户主动要求处理 issues。
- archive 后用户选择继续清理本次产生或关联的 issues。

步骤:
1. 运行 `pnpm harness:issues`, 获取 active / resolved 数量和 active issue 列表。
2. 逐个阅读 active issue, 只处理用户指定范围; 未指定时先分析 issue 依赖关系和优先级并排序, 然后根据优先级处理。
3. 分类:
   - 已修复: 补完成日期、解决说明、关联 commit/PR/任务, 移入 `docs/issues/resolved/`。
   - 仍有效且值得做: 确认是否已有 GitHub Issue; 没有则创建或绑定, 后续用 `harness-0.0-new` 建 work。
   - 重复或过期: 写明原因后移入 `docs/issues/resolved/`。
   - **裁决不做 (2026-07-04)**: 移入 `docs/issues/rejected/` — 写耐久理由 (真权衡, 非临时环境; 临时原因属 deferral 应留 active) + 概念别名; 归档 work 的 D 裁决里"明确不做"的方案也在此落一条, 防半年后被重新提出。
   - 与当前任务相关但不在当前验收范围: 保持交叉引用, 不顺手修。
4. 若需要代码改动, 不在本动作内直接改; 新开或续跑对应 work。
5. 处理后运行 `pnpm harness:check`。

产出: `docs/issues/` 中一组已收敛的问题记录, 或明确的新 work 入口。
